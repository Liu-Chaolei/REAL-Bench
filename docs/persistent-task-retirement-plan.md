# 旧 Persistent Task 运行链路退役计划

状态：已实施。旧配置、运行、恢复和重新评分入口已退役；公共证据接口与历史结果读取保留。

## 1. 目标与范围

用户已明确不再使用旧 Persistent Task 配置。本轮退役旧 `persistent_task_config` 对应的运行链路，保留当前需要的两种后台交互：

- 普通动态后台请求：`active_metrics.persistent_task`。
- Modify／Cancel／AddTask 交互变体：独立场景机制。

保留新机制共用的后台事件模型、Provider 适配和证据读取能力。

历史结果保留读取及已保存分数的展示；旧机制的重新运行、断点续跑、自动回放和重新评分退出正式支持范围。已有结果文件和冻结任务数据不因本轮整理而被改写或删除。

实施主要依靠入口移除、依赖断开和明确的对象职责。不得为这次删除往正式评测系统中增加全量审计、自动修复或额外裁判流程。

## 2. 当前依据

此前检查发现：

- Gaia2 主任务文件的 1000 道任务均未嵌入旧 `async_interaction` 配置。
- 独立交互变体使用 `gaia2-interaction-variant-v1` 契约。
- CLI、Runner 和编排器仍保留显式启动旧 Persistent Task 的入口。
- 旧固定 async 和 Persistent Task sidecar 材料已经移除，部分旧验收脚本仍依赖这些材料。
- 新 active 和交互变体仍引用 `persistent_tasks/` 下的公共代码，因此不能整目录删除。
- 旧结果重新评分依赖旧 replay、coordinator 和配置模型；只关闭 CLI 不足以删除整套旧实现。

这些是删除边界的依据，不应转化为每次评测都执行的数据扫描。实施时只需核对涉及文件的当前依赖，尊重工作区已有改动。

## 3. 删除后的运行规则

### 3.1 新运行

新运行只允许使用新 active 配置或交互变体契约，旧 `persistent_task_config` 不再参与：

- 任务与环境构造；
- Agent 启动和能力检查；
- 请求注入、后台调度和阶段阻塞；
- 运行摘要生成；
- 主任务奖励组合；
- checkpoint 恢复。

新 active 与交互变体的并用策略不属于本次旧机制退役范围，沿用各自现有装配规则，不借此扩展或改变测试条件。

### 3.2 遇到旧配置

- 旧 CLI 参数由参数解析器拒绝。
- Python／JSON 运行配置中出现非空旧字段时，在配置加载入口明确报错。
- 当前任务若仍嵌入旧异步契约，应在本次任务加载时拒绝；不能把它静默当成普通任务。
- 交互变体仍使用的 `scenario.async_interaction` 字段保留，按契约版本区分。
- 不把旧配置自动转换为新 active 配置。
- 不静默丢弃旧配置后继续运行。

配置模型若默认忽略未知字段，需要在移除字段时保留一个小型拒绝规则。该规则只检查本次加载的配置或任务，不建立通用迁移框架，不扫描整个数据集。

### 3.3 历史结果

历史结果读取与新运行配置校验分开：

- 读取已有轨迹、后台摘要和已保存评分。
- 历史配置作为结果中的普通数据保留，不实例化旧运行时。
- 没有保存分数时显示未评分，不能填零或自动调用旧 grader。
- 请求旧机制重新评分或恢复运行时，明确说明该协议已退役。

## 5. 移除旧编排器挂接

从普通和全双工编排器中删除仅服务旧路径的行为：

- `persistent_task_runtime` 的安装、读取与推进。
- 旧 `persistent.blocks_stage()` 阶段阻塞条件。
- 旧 coordinator 的交付开始、完成和 Agent 回复通知。
- 普通用户插话触发旧回复窗口关闭的逻辑。
- 旧 source event completion 队列与专属 listener。
- 旧摘要写入 `info["persistent_tasks"]` 的新运行分支。
- 旧 finalization、异常清理和证据落盘调用。

`async_evidence_source` 按调用方处理：

- 删除旧 coordinator 专用的编排器属性与挂接。
- 保留 Agent 暴露后台证据的接口，以及新机制实际依赖的能力和状态读取。

保持 `ScenarioStages`、工具排空、STOP 处理和实际音频交付的现有规则。不要把旧机制退役扩大成阶段控制或语音时序重构。

完成这一步后，正常运行链路应无法再进入旧请求调度器。

## 6. 拆开公共依赖后删除旧模块

### 6.1 保留的公共能力

按实际调用方保留：

- `BackendTaskObservation`、`CanonicalState` 等公共事件和状态模型。
- 新 active policy 使用的类型与必要工具函数。
- Qwen 等当前 Provider 使用的后台事件适配器。
- `get_async_evidence_source()` 和公共 `evidence_source()`。
- `scores.py` 中仍被当前指标或历史展示使用的分数读取、整理函数。

保留这些能力不要求继续保留旧配置入口或旧调度器。

### 6.2 必须先处理的交叉依赖

当前公共导入与旧代码存在交叉：

- Qwen adapter 和公共 observation 模块引用旧 `ObservedEvent`。
- `adapters/__init__.py` 导入旧 in-memory adapter。
- `persistent_tasks/__init__.py` 导入旧服务、模型和运行时。
- 部分顶层模块只向 `legacy/` 转发兼容导出。

处理顺序：

1. 确认新机制实际调用的 adapter 方法和事件转换路径。
2. 将新路径确实需要的类型留在公共模型模块。
3. 删除仅服务旧接口的方法、类型和导出。
4. 精简包初始化，使导入公共模型或当前 adapter 不再隐式加载旧服务与调度器。
5. 删除失去所有生产调用方的旧模块。

不复制多份公共代码，不为这次退役顺便引入大型 Provider 接口重构。

### 6.3 候选删除范围

以下是依赖清理后的候选范围，不是按目录无条件删除：

- `persistent_tasks/integration.py`。
- 旧 coordinator、trigger scheduler、reply window、operation attribution、finalization。
- 旧 in-memory service、scheduler、projection 和 fixture runtime。
- 仅服务旧运行的配置模型与 overlay。
- 已失去用途的顶层兼容包装。
- Gaia2 固定 Persistent Task sidecar loader 及专属注册入口。

每个文件以剩余调用方为准；其中仍被新机制使用的公共定义先提取或保留，再删除旧实现。

## 7. 清理旧评分与回放链路

### 7.1 正式 evaluator

删除仅为旧 Persistent Task 服务的：

- 根据 `info["persistent_tasks"]` 自动调用旧 grader 的分支。
- 旧 business overlay 评分分支。
- 旧 `combine_reward` 和 `PERSISTENT_TASK` 奖励组合逻辑。
- 旧后台回复证据选择分支。
- 评分前执行旧 replay 的逻辑。
- 旧证据版本分派到 legacy grader 的自动调用。

新 active 完成分、交互变体评分和普通 Gaia2 任务评分保持各自现有业务含义。

### 7.2 最小历史读取

历史读取保留：

- 原始历史轨迹与摘要。
- 已保存的分数及状态。
- 历史结果反序列化必要的字段和枚举。

例如旧结果可能含有 `PERSISTENT_TASK` 奖励枚举。可以继续识别这个枚举，但新运行不能再选择对应的旧评分路径。

读取旧结果不应触发代码执行、重放或模型调用。历史缺少评分时展示未评分；用户主动要求旧协议重新评分时明确返回不支持，不套用新规则。

### 7.3 删除剩余旧评分模块

取消旧重新评分支持后，检查并删除无调用方的：

- 旧 grader 与 legacy grading。
- 旧 replay 和 evidence 校验专属代码。
- 旧 coordinator、调度和窗口依赖。
- `PersistentTaskConfig` 及旧 overlay 模型。
- 对应兼容导出。

这一步用于解除“为了重算旧结果而保留整套旧运行时”的依赖。必要的历史分数字段读取函数仍可保留。

## 9. 轻量验证

优先复用现有测试，只补充新增退役边界所需的小型用例：

1. 旧 CLI 参数不能启动运行。
2. 非空旧配置字段、旧任务异步契约和旧 checkpoint 恢复被明确拒绝。
3. 新 active 能观察后台事件、注入请求并评分。
4. Modify／Cancel／AddTask 专项测试继续通过。
5. 公共模型及 Qwen 证据 adapter 能导入并处理代表性事件。
6. 小型历史结果能读取并展示保存分数；读取过程不触发旧 replay 或 grader。

最后执行改动文件的 Ruff 检查和对应的小范围测试。

不要求：

- 全量 Gaia2 1000 题运行。
- 真实 Provider API 调用。
- 额外 LLM 验收。
- 全量历史结果回放。
- 全仓库修复或与本次无关的清理。

现有工作区若存在无关测试失败，应记录具体原因，不为完成本次退役扩大修复范围。

## 10. 正式评测中的机制约束

正式运行只保留必要的轻量边界：

- 加载本次配置时拒绝已退役字段。
- 加载本次任务时区分交互变体契约和已退役异步契约。
- 恢复本次 checkpoint 时拒绝旧协议。
- 根据当前配置安装新机制。

不得加入：

- 每次启动遍历旧代码或整个数据目录。
- 运行时扫描依赖关系。
- 自动迁移、补全或修复旧配置。
- 为确认删除安全而回放整套任务。
- 多层验收状态、额外模型裁判或后台一致性巡检。

这些边界通过入口和依赖关系实现，不把代码整理任务变成评测系统的新运行负担。

## 11. 实施顺序

### 改动单元一：退出新运行

1. 删除 CLI 和 smoke 旧入口。
2. 移除运行配置字段和 Runner 参数链。
3. 建立旧配置、旧任务契约和旧 checkpoint 的加载拒绝规则。
4. 删除编排器旧运行时挂接。
5. 删除依赖固定 async 数据的启动与验收脚本。

结果：旧机制无法启动或恢复，新机制仍使用当前入口。

### 改动单元二：删除旧实现

1. 拆开公共 adapter、事件类型和包初始化中的旧依赖。
2. 移除正式 evaluator 中的旧评分与奖励组合分支。
3. 取消旧协议自动回放和重新评分。
4. 删除无调用方的旧配置、调度、回放、评分和兼容包装模块。
5. 清理旧 sidecar loader 和专属注册入口。

结果：新机制不再通过公共导入间接加载旧实现。

### 改动单元三：收尾

1. 保留最小历史结果反序列化和已保存分数展示。
2. 更新或删除对应测试。
3. 更新当前文档并标记历史方案。
4. 运行针对性测试与 Ruff。
5. 汇总实际删除项、保留的公共能力和验证限制。

每个单元完成后保持相关模块可以导入；无需引入额外迁移工具或通用兼容框架。

## 12. 完成标准

- 新运行不存在旧 `persistent_task_config` 的有效启动路径。
- 旧配置不能被静默忽略或自动转换后执行。
- 编排器不再推进旧 coordinator，也不再应用旧阶段阻塞与回复窗口规则。
- 新 active 和交互变体继续使用公共后台证据能力。
- 公共导入不再隐式依赖已退役服务。
- 历史结果可读、已有分数可展示；不会隐式执行旧回放或重新评分。
- 冻结任务和已有结果文件保持原样。
- 正式评测没有新增全量验收、自动修复或额外裁判流程。
