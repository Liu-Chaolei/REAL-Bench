# GAIA2 连续任务接入 τ 与 Qwen Audio Agent：详细实施计划

## 1. 目标与已确定的方案

从现有 800 个三阶段连续任务中使用已经固定的 10 题，执行真实语音测试。
每题只有一次 Agent 会话、一个应用环境、一条场景时钟和一个最终任务分数。

已经确定：

1. 复用 τ 用户模拟器的结束判断和 `###STOP###`，不增加完成判定模型。
2. 信息可见范围保持现状，不增加权限层、过滤器、可见范围接入检查或专项测试。
3. 三阶段全部结束后统一评分；运行时不评分，不给三个独立阶段分数。

后续请求通过现有脚本队列和 TTS/音频机制投递。阶段之间保留实际历史与应用
状态；前阶段做错后也使用这个真实状态。用户 STOP 只是交互控制信号，不证明成功。
任务文本、原始 ID、参考答案和生成审核材料无需重新编写。

## 2. 当前基础与真正需要改动的地方

现有基础：800 题都已加载为原生 Task，scenario.stages 保存三个请求及各自
标准；Qwen 镜像 0.5.2 声明支持 GAIA2；共享工具、音频和最终状态评分已经存在。
固定 10 题的参考执行与严格回放通过，13 项数据结构和域能力测试通过。
这些结果不是在线三阶段流程或模型准确率的证明。

当前缺口：

- FullDuplexOrchestrator 遇到任意用户结束标记会立即置 done=True。
- 扩展请求仍由 scenario.events 的参考依赖触发，可能永远不释放或重复释放。
- STOP 已进入用户生成过程，若只取消 done 而继续传递原 chunk，可能把控制
  标记传给 Agent，或让用户下一轮继续停在旧目标。
- 当前合并通信要求面向整段对话，缺少各要求对应的实际阶段窗口。
- manifest 仍标记 verified=false、execution_ready=false，正常运行被现有门禁拦住。

不需要新写评测平台、Qwen bridge 或容器镜像。只有发现现有媒体接口确实缺少
必需能力时才改 provider；先通过 τ 编排层完成此次接入。

## 3. 阶段控制器

### 3.1 放置位置和最小接口

新增 `src/tau2/orchestrator/scenario_stages.py`，由编排器持有。
控制器使用 scenario.stages 和既有扩展用户事件 ID，维护：

- current_stage：当前阶段号，使用数据中的 0、1、2。
- phase：active、transition_pending、request_pending、finished。
- 当前请求是否实际开始送达、是否完整播放。
- 已消费的 STOP 及每次转换的日志序号/tick，避免同一个信号重复推进。

建议接口：`handle_user_stop`、`pending_request`、`observe_delivery`、`summary`。
具体类名可按仓库风格调整。控制器不执行金标操作、不读取评分结果，也不负责
决定 Agent 做对没有。仅在含多个 scenario.stages 的任务上启用。

### 3.2 STOP 的处理规则

- 当前阶段为 0 或 1，用户发出普通 STOP：记录信号，进入 transition_pending，
  消费这个控制消息，保持整个仿真运行。
- 当前阶段为 2，用户发出 STOP：沿用 USER_STOP 和现有收尾/评分流程。
- 没有 STOP：继续原来的等待、澄清、用户回复和工具执行，不增加阶段判定调用。
- TRANSFER、OUT-OF-SCOPE、Agent STOP、连接故障、总超时与错误上限：走现有
  终止或异常路径，记录尚未送达的阶段。
- 混合控制标记不能误走普通 STOP 推进；终止类标记优先按原终止路径处理。

现有 STOP 也可能来自用户放弃等待。首版仍复用现有判断，不额外增加停止原因
分类模型。因此，转换记录只写“用户发出 STOP”，不标注“本阶段成功”。
最终评分负责判断任务是否真正完成。

### 3.3 拦截位置与用户续接

在 `_process_participant_turn` 的 `is_stop(new_chunk)` 分支中，先让控制器
处理用户普通 STOP。已消费时返回正常无语音等待 chunk，不置 done、不设置
整题 termination_reason，不把 STOP 传给 Qwen 或当作用户语音合成。
保留原始 STOP 为运行诊断，避免把它当作普通对话重放到 Agent。

复用 `queue_scenario_input` 排队下一条固定请求，以及当前用户模拟器对已释放
请求的上下文追加逻辑。用户在开始处理下一请求时应以该请求为当前目标；这
是阶段续接逻辑，不新增信息可见范围机制。保留之前的对话和已知事实。

消除旧阶段遗留的待提交普通回复/STOP 候选，但不清空会话历史、不重建用户
或 Agent、不重新连接 Qwen、不重置 ASR/TTS 整条音频链路。已有异步候选作废
机制和脚本输入优先机制应直接复用。

### 3.4 转换期间保持音频和工具运行

STOP 后暂不直接插入下一条语音。继续 tick，使在途工具完成、结果送达
Agent，并让已有 Agent 音频正常播放。使用现有队列状态与播放状态判断收尾，
不引入固定 sleep 或新的业务判定。

可发送下一请求时，使用既有事件 ID 入队一次。下一阶段的开始时间以首个
实际送到 Agent 的请求音频样本为准，完整播放单独记录。中断不自动表示
整条请求已经说完；沿用现有重复/澄清机制。超时继续由现有总时限和工具时限
约束，不能因等待转换无限挂起。

阶段之间保持真实场景时间推进，环境通知也继续到达，不暂停世界时间。

## 4. 与原始场景事件的衔接

修改 `environment/scenario.py`：在线运行时，将两个扩展阶段请求标记为由
控制器释放，使 `advance()` 不再自动按参考叶节点释放这两个请求。
识别依据使用 stages.event_ids 与现有用户事件，不硬编码某个具体任务 ID。

同时从仅服务于这些扩展请求的 needed-anchor 计算中移除相应需求，避免继续
为释放下一阶段要求完整匹配参考操作。原始任务内的澄清消息、通知和其他
环境事件仍按原本依赖与延时执行，不伪造它们的参考父节点已经完成。

下一请求实际送达时，仍通过原来的 delivered(..., event_id=...) 记录输入；
它会建立该请求的真实送达结果。不得为了“解锁”而把前面未发生的参考操作
填入 completed/results。

参考执行仍可遍历原始完整事件图；回放只重放实际记录，不自动释放脚本请求。
在线控制、离线参考与回放使用显式调用参数区分，避免改写已保存的题目图。
参数要传入重放环境构造，保证同一运行语义。新增影响语义的源码加入 runtime_digest。

文本与语音使用同一控制器和 STOP 规则；文本模式只需在现有用户结束分支
续接下一请求。第一轮真实验收重点是 Qwen 的全双工语音路径。

## 5. 信息传递沿用现状

维持当前 Agent、用户模拟器、工具与环境之间的数据流。任务阶段在同一会话
内自然累积；未成功创建的订单、消息或日程不会被参考执行自动补齐。
不增加信息权限设计、过滤器、可见范围接入检查或对应专项测试。

## 6. 运行记录：只保存统一评分需要的边界

优先在已有 `SimulationRun.info` 增加可序列化的 scenario_series 运行摘要，
避免为此引入另一份任务数据或多套阶段成绩模型。摘要包含：

- 运行协议版本、当前/已到达阶段。
- 每条请求的 event_id、排队、首次实际送达、完整播放或中断记录。
- 各次用户 STOP、转换边界、tick 和对应执行日志序号。
- 整题停止原因与尚未到达阶段。

现有 environment_trace 继续保存实际工具、环境及语音证据；阶段摘要引用
它的日志序号。保留 STOP 与音频事件区别。转换失败或早停也要保存部分摘要。
不在边界复制三份数据库，不运行阶段评分。所有实际轨迹按现有方式在评分前落盘。

## 7. 三阶段统一评分

### 7.1 入口和整题结果

在现有 `evaluate_simulation` 的多阶段分支接入统一证据视图，复用原有 ENV、
COMMUNICATE、NL 组合与 judge 配置，最终输出一个 reward_info。
只有整题结束后才启动评分；一次统一评测可以包含既有多个组件/模型调用。

正式总分继续按题目 reward_basis 乘积合成。三条请求未全部实际送达，不能因
最终状态偶然正确而给整题通过；普通早停是 Agent 结果，基础设施/评分异常
沿用现有独立分类。不能把前两次内部 STOP 写成整题 USER_STOP。

记录连续任务评分协议版本，保留历史单阶段分数的含义。

### 7.2 最终业务状态

复用 GAIA2 check_goal：参考执行产生三阶段累计的最终目标，再与真实执行
结束后的业务状态比较。继续使用生成实体结构匹配和受保护状态规则。
后续明确要求修改的对象按最后要求判断，不同时强制保留被合法修改的旧值。
不要求 Agent 完成与参考相同的工具顺序或相同数量的读取。

### 7.3 回答和过程要求

从 stages 中提取原始通信与 NL 条件，保留条件所属阶段。

- COMMUNICATE 检查相应阶段实际播放的回答，不让下一阶段才说出的答案补掉
  本应在之前回答的要求。调用时可以按条件提供相应窗口，但不产出阶段总分。
- NL 检查使用完整实际对话、工具/环境证据与边界，明确每个条件适用的阶段。
  例如“第二阶段不得再次购买”检查该时段实际操作，“原日程先查询再修改”
  检查真实顺序。合法后续修改不追溯否定先前行为。
- 动态 ID 和结果占位符使用实际工具结果/实体映射解析；实体未创建是缺失或
  依赖失败。映射不能以整题业务状态已经完全正确为前提，也不能代入金标实体。
- 现有语义 judge、缺失/重复 judge 输出处理、费用记录和错误保存继续复用。

### 7.4 现有 authoring checks 如何处理

数据中的 checks 含有大量对参考解法本身的验证。例如要求“参考 getter 返回的
ID 与参考创建操作返回的 ID 一致”，不能因此强制真实 Agent 也调用这个 getter。
全部 800 题有 12,456 条此类检查；固定 10 题有 147 条，其中 121 条引用参考
操作结果，26 条引用状态。不能把缺少某个参考读取直接算作模型业务失败。

这些检查首先保留在离线参考验证中，不机械地全部加入在线硬评分。
线上使用已有任务业务目标、通信和 NL 标准；若某项真实业务要求只存在于 checks，
把它转换为结果/历史证据条件，而非参考调用要求。优先对固定样本确认这种
评分适配，采用共享规则，不为每个任务写单独评分脚本或改写题目。

确需中间业务状态的要求，在整题结束后按日志前缀恢复对应时刻。只对需要的
条件执行恢复，不建立在线阶段检查点系统。恢复逻辑放在运行评分模块，不让
在线 evaluator 依赖生成、修复或审核流水线。

## 8. 代码修改清单

- 新增 `orchestrator/scenario_stages.py`：轻量阶段控制及运行摘要。
- `orchestrator/full_duplex_orchestrator.py`：消费用户 STOP、等待收尾、释放
  下一请求、观察实际投递、收集摘要。
- `orchestrator/orchestrator.py`：控制器初始化、文本续接、统一收尾摘要。
- `user/user_simulator_streaming.py`、必要时 `user_simulator.py`：复用脚本请求
  续接与异步候选作废，仅调整阶段续接所需的状态，不新增可见范围机制。
- `environment/scenario.py`：在线托管扩展请求，保留原始环境事件调度。
- `environment/replay.py`：仅在需要时增加日志边界恢复复用点，保持严格回放。
- `evaluator/evaluator.py`、`evaluator/scenario.py`：统一证据、整题到达条件、
  历史证据与整题合成；通信/NL 的文本与语音变体保持一致。
- `evaluator/evaluator_communicate.py`、`evaluator/evaluator_nl_assertions.py`：
  在复用接口不足时补充边界/证据参数，不另建 judge 系统。
- `domains/gaia2/scoring.py`：仅补必要的部分结果/实体映射能力。
- `domains/gaia2/verify.py`、`environment.py`、`utils.py`：参考验证、运行身份
  绑定与当前 execution_ready 状态的准确处理。
- 现有 smoke 启动器、结果查看/重评分入口优先复用；补一个读取固定 10 题
  清单的薄启动脚本即可，不新建任务运行框架。

## 9. 实施批次和测试

### A. 控制器与 STOP 接入

完成最小控制器与两种编排模式接入，用假的 Agent/用户验证三次 STOP 对应
两次转换和一次整题结束。验证已消费 STOP 不会送到 Agent，不重建会话或
环境，不因重复生成结果跳过阶段，非普通 STOP 保持终止行为。

### B. 实际语音投递和原始环境事件

接入脚本队列与真实投递标记，验证请求自动释放与控制器释放不会重复，
阶段转换时旧异步回复不会抢占新请求。覆盖音频中断、在途工具返回、总超时，
以及 time/ambiguity 类任务原有环境通知和澄清条件。

### C. 统一评分

至少覆盖：正常三阶段、后续合法修改、阶段内禁止操作、答错后下一阶段补答、
对象未创建、不同生成 ID、不同但正确的读取路径、未到达第三阶段、judge 失败
保留轨迹，以及相同记录独立重评分一致。运行时不得调用新完成判定或评分模型。

A/B/C 仅编写行为有实质区别的必要测试，不增加信息可见范围专项测试。
跑相关 GAIA2、scenario、streaming、evaluator 和 Qwen 域能力回归。
运行 make check-all；无需为本次文档计划运行测试。代码改动完成后再执行这些检查。

### D. 参考验证与现有门禁

先用固定 10 题离线参考/严格回放快速定位问题，再按现有 seal 机制执行
完整 800 题参考/回放验证。完整检查是现有数据启动绑定的要求，不是新增
800 题真实模型评测，也不涉及 800 题重新生成。

参考数据、资源与运行代码摘要全部对应后，由验证命令写入新运行绑定和
连续任务能力版本。更新 verified/execution_ready 的逻辑，明确区分“可启动
试跑”与“已完成真实样本验收”。不手工把布尔值改成 true，也不绕过门禁。
离线命令不得调用用户或 Agent 模型；语义评分的线上能力由 C 类测试及真实试跑验证。

## 10. 固定 10 题真实试跑

样本位于：
`data/simulations/gaia2-series-smoke-preflight-20261106-105704/selection.json`。
随机种子 300，五个类别各 2 题；现有 task-ids.txt 保存完整原始 ID。

建议先以 0353 执行类任务验证端到端链路，再完成其他 9 题。先跑题仍在
本批 10 题内，不因失败换题。若修复运行代码再测，新建结果版本保留首次尝试。

默认计划参数：

- Qwen 配置：integrations/qwen_audio_agent/config.gaia2.example.json。
- domain=gaia2，benchmark=none，language=en，audio-native-provider=qwen_agent。
- 每题 1 次，seed=300，单并发，自动重试和幻觉重试均为 0。
- 首轮建议单题总对话预算 1200 秒，三个阶段共享，不在转换时重置；沿用
  smoke 的额外 150 秒墙钟余量。实际超时与任务内的定时业务要求分别记录。
- 使用原有 verbose-logs、audio-taps 与独立输出目录。配置继续引用已有私有
  环境文件，不把凭据写入命令或结果。

通过普通 run_hpc.sh smoke/tau2 run 执行，不使用参考执行器模拟 Agent。
薄启动脚本负责读取样本、分批运行并汇总首题及剩余题结果；使用不同子目录
避免 results.json 的恢复计划或 task-ids 绑定不一致。

真实试跑后记录每次尝试：任务 ID、三个请求送达情况、STOP 与转换位置、
最终终止原因、整题 reward 和组件检查原因、基础设施/用户/评分错误、
音频及轨迹路径。整题完成率使用有效题目作为分母，同时列明全部 10 次尝试。
阶段仅报告到达情况，不产生三个阶段独立分数。

## 11. 交付与完成标准

交付修改代码、必要测试、验证记录和固定 10 题的结果报告。报告给出运行机制
是否可用、Agent 的整题完成情况和具体失败原因；二者分别说明。

完成标准：

1. 正常走完的题有三次真实请求投递，前两次 STOP 推进、最后一次结束。
2. 三阶段使用同一 Qwen 会话、真实应用状态和连续时钟。
3. 评分只在整题结束后执行，得到一个整题结果，过程条件仍有依据。
4. 早停和异常可解释，实际轨迹评分前保存，正常轨迹可严格回放。
5. 固定 10 题都有可追溯尝试；任务失败照实报告，不要求模型全部做对。

不要求上线新排行榜、发布数据集、重写题目、增加信息检查体系或扩跑 800 题
真实评测。本文件是实施计划，运行代码及真实测试尚未执行。
