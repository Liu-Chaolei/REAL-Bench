# Persistent task interaction triggers

本文档记录异步持久化任务评测中，用户何时发出任务关联、状态查询、修改、取消和结果请求的设计。当前只讨论同一次持续语音会话内的触发；跨通话恢复、失败重试、权限变化和语音交互干扰属于其他 pipeline。

## 核心原则

用户模拟器不自行决定何时提出关键任务问题。场景调度器根据后台任务状态和事件时间线释放预先定义的用户请求，用户模拟器再负责把已经释放的请求转换成自然语言或语音。

这样可以保证：

- 每道题都会稳定触发需要评测的任务操作；
- 不同模型不会因为自行选择发问时机而产生不可比结果；
- Agent 失败和用户没有触发问题可以明确区分；
- 离线参考执行和在线语音执行可以使用同一套事件边界；
- 回放时可以复现用户问题的释放顺序。

LLM 负责“怎么说”，场景调度器负责“什么时候释放”。第一版可以直接使用固定请求文本；触发机制稳定后，再为同一个触发点增加几种自然语言改写。

## 当前 tau-bench 调度方式

当前场景事件由 `ScenarioRuntime` 管理。初始用户事件进入用户输入队列；用户模拟器消费队列后才生成用户消息。队列为空时，用户模拟器才根据 Agent 最近的回复生成自由回复。

现有连续 Gaia2 阶段主要由 Agent STOP 控制：用户完成当前请求、Agent 发送 STOP 后，`ScenarioStages` 释放下一段预设请求。后台环境事件则根据事件依赖和 `delay_seconds` 由场景运行时推进。full-duplex 模式下，语音 tick、工具执行、后台事件和用户输入可以并行推进。

异步任务评测应复用这套事件图和队列机制，但增加基于后台任务状态的用户事件释放条件。STOP 可以作为自然轮次边界，不能成为唯一触发依据。

## 建议的触发模型

每个场景包含一个评测侧任务账本、后台状态时间线和用户事件列表。用户看不到内部任务 ID、触发条件或完整状态时间线。

```text
后台任务状态或事件发生
        ↓
触发条件满足
        ↓
可选的最小时间延迟结束
        ↓
等待当前 Agent 回复或语音播放完成
        ↓
场景调度器释放用户请求
        ↓
用户模拟器生成文本或语音
```

第一版的释放条件建议为：

```text
release = 状态/事件条件满足
          + 最小时间延迟
          + 当前用户/Agent 轮次达到边界
```

状态条件保证问题在正确的任务阶段出现；最小延迟避免状态刚变化就立即插话；轮次边界保证持续语音中仍有清晰的评测窗口。

## 触发方式

### 相对时间触发

在某个已知事件后等待一段时间，再释放用户问题：

```text
初始任务请求完成后 10 秒：
“刚才那个任务现在进行到哪一步了？”
```

适合测试固定等待期间的查询，但单独使用时不稳定，因为 Agent 的工具调用和语音回复速度不同。单独使用前应确认任务已经进入预期状态；更推荐与状态或事件条件结合。

### 任务状态触发

当任务进入指定状态时释放请求：

```text
task_1.status == running
→ “修 bug 的那个现在到哪一步了？”

task_1.status == completed
→ “刚才那个任务完成了吗？结果怎么样？”
```

适合测试运行中查询、完成后结果接收和取消后的状态确认。

### 任务进度触发

当任务到达指定步骤或进度时释放请求：

```text
task_1.progress == 3/5
→ “修 bug 的那个现在进行到哪一步了？”
```

适合检查 Agent 是否能正确报告当前步骤、已完成步骤和下一步。

### 后台事件触发

当后台发生明确生命周期事件时释放请求：

```text
task_1 entered_step("running_tests")
→ “现在是在跑测试吗？”

task_1 completed
→ “把刚才那个任务的结果告诉我。”
```

事件触发比固定等待更稳定，应作为主要触发方式。

### Agent 行为触发

某些问题可以在 Agent 完成一个可记录的行为后释放：

```text
Agent 查询 task_1 状态并完成回复
→ “你刚才说的那个任务，现在具体到哪一步了？”
```

这种方式只能绑定到实际工具调用、实际消息或已记录的 Agent 行为，不能只绑定到 Agent 的口头承诺。它适合测试连续追问，不应作为所有场景的默认方式。

## 建议的数据结构

异步任务不需要用户在当前场景中创建。任务在场景初始化时已经存在于评测侧账本中。

```json
{
  "tasks": [
    {
      "task_id": "task_1",
      "title": "修复登录 bug",
      "goal": "修复并运行测试",
      "state": "running",
      "progress": {
        "completed_steps": 2,
        "total_steps": 5,
        "current_step": "运行测试"
      },
      "result": null
    }
  ],
  "background_events": [
    {
      "id": "task_1_running_tests",
      "kind": "task_state",
      "task_id": "task_1",
      "state": "running",
      "progress": {
        "completed_steps": 3,
        "total_steps": 5,
        "current_step": "运行测试"
      },
      "delay_seconds": 8
    },
    {
      "id": "task_1_completed",
      "kind": "task_state",
      "task_id": "task_1",
      "state": "completed",
      "dependencies": ["task_1_running_tests"],
      "delay_seconds": 15,
      "result": {
        "summary": "修复完成，测试全部通过"
      }
    }
  ],
  "user_events": [
    {
      "id": "user_query_progress",
      "kind": "user",
      "arguments": {
        "content": "修 bug 的那个现在到哪一步了？"
      },
      "release_condition": {
        "event_id": "task_1_running_tests",
        "delay_seconds": 2,
        "after_turn_boundary": true
      }
    },
    {
      "id": "user_query_result",
      "kind": "user",
      "arguments": {
        "content": "把刚才那个任务的结果告诉我。"
      },
      "release_condition": {
        "event_id": "task_1_completed",
        "delay_seconds": 1,
        "after_turn_boundary": true
      }
    }
  ]
}
```

`release_condition` 只供场景调度器使用，不进入 Agent 或用户模拟器的提示词。任务 ID、状态时间线、结果和预期操作也只留在评测侧。

如果沿用现有 `ScenarioAction`，可以先使用已有字段：

- `dependencies` 表示后台事件和用户事件的因果关系；
- `delay_seconds` 表示依赖完成后的最小延迟；
- `kind="environment"` 表示后台状态变化；
- `kind="user"` 表示释放给用户模拟器的请求。

对于无法只用依赖和延迟表达的状态条件，再增加私有的 `release_condition` 字段。该字段不改变用户可见的任务结构，也不参与 Agent 工具 schema。

## 一条完整场景示例

初始化时存在三个后台任务：

```text
task_1：修复登录 bug，running
task_2：生成销售报告，waiting
task_3：部署测试环境，completed
```

后台时间线：

```text
t=5：task_1 进入 running_tests
t=8：task_2 进入 running
t=12：task_3 的结果可用
```

用户事件：

```text
task_1 进入 running_tests 后 1 秒：
“修 bug 的那个现在到哪一步了？”

task_2 进入 running 后 1 秒：
“报告任务呢？它是在等什么？”

task_3 结果可用后 1 秒：
“第几个任务已经完成了？把结果告诉我。”

用户完成上一轮后再等待 3 秒：
“把修 bug 的那个停掉。”
```

Agent 应该分别将这些问题绑定到 `task_1`、`task_2` 和 `task_3`，不能因为任务名称相似、完成时间接近或用户使用“那个”而混淆任务。

## 触发时机的边界规则

### 不在 Agent 回复中间释放

默认等待当前 Agent 回复或语音播放完成，再释放下一句。这样可以避免用户查询和 Agent 的上一句播报互相覆盖，也便于按阶段计算通信结果。

### 状态不满足时不释放

如果任务没有进入目标状态，用户问题保持待释放状态，不提前发送。比如要求查询“已完成任务”的问题，不能在任务仍处于 `running` 时提前发出。

### 任务提前完成时立即满足条件

如果任务比计划更早进入目标状态，事件按实际状态变化触发，并保留实际场景时间。不能把问题回填到计划时间。

### 多个条件同时满足时保持事件顺序

同一时刻有多个用户事件可释放时，使用显式优先级或事件序号稳定排序。所有事件仍记录真实的排队、开始和完成时间。

### 用户取消当前任务后停止不相关追问

如果用户已经取消某任务，后续针对该任务的“进度查询”或“完成结果”事件应标记为不再释放，除非该题明确要求用户确认取消结果。

### Agent 没有结束当前轮时暂存请求

触发条件满足但当前轮仍在进行时，事件进入待释放队列。等轮次边界到达后再交给用户模拟器，并记录排队时间和实际投递时间。

## 与现有实现的对应关系

现有流程可以按以下方式复用：

1. `ScenarioRuntime` 继续负责场景时钟、依赖、后台事件和可回放日志。
2. `runtime.user_inputs` 继续作为用户输入队列。
3. 半双工 orchestrator 在每轮开始前取出已释放的用户输入。
4. full-duplex orchestrator 在语音 tick 中保留排队、播放和实际投递边界。
5. `ScenarioStages` 的 STOP 逻辑继续用于普通连续请求；异步任务查询使用状态/事件触发器。
6. 用户模拟器继续优先消费预设输入；没有预设输入时才生成普通自由回复。

第一版不需要让用户模拟器自己维护后台任务状态，也不需要把完整任务账本放进用户提示词。任务状态变化由场景运行时产生，用户请求由调度器释放。

## 推荐的第一版实现顺序

1. 定义评测侧任务账本和任务状态时间线。
2. 增加状态/进度事件和完成事件的调度能力。
3. 增加带 `after_turn_boundary` 和最小延迟的用户事件释放条件。
4. 记录“条件满足时间、排队时间、实际投递时间”三个时间点。
5. 做单任务查询、双任务关联和任务完成后结果查询的离线回放。
6. 再加入修改、取消和多任务交错场景。
7. 最后接入持续语音运行，复用相同事件图检查实际播放窗口。

第一版应固定“什么时候发问”，让模型只面对“如何理解和处理这句任务请求”的问题。触发机制通过离线回放验证后，再扩展用户话术和语音表现。
