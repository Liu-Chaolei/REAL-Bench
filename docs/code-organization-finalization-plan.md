# 代码整理收尾与数据版本对齐计划

状态：本轮整理已实施。Provider 移除、Gaia2 主入口清理和状态清单更新已完成；参考修复已对应为候选修订，因 67 道 unresolved 与最终封存尚未完成，按本计划保留候选状态，未切换活动任务。实施结果见[当前状态清单](code-organization-discussion.md)及[参考修复收尾记录](gaia2-reference-finalization-report.md)。

## 1. 本轮目标

按已形成的共识推进四项工作：

1. 删除尚未完整适配的 GPT Live、Gemini Live 接入，不迁移到新 Adapter 目录。
2. 清理 Gaia2 主入口中的旧领域残留。
3. 将代码整理讨论稿更新为当前状态清单。
4. 完成正式版本边界与参考数据修复收尾。

以下两项明确暂缓，不混入本轮：

- 错误、重试与统计口径整理。
- 默认采集行为及各指标事实依据整理。

本轮以删除入口、断开无用依赖、明确配置和版本归属为主。验证只用小范围本地测试和必要的离线数据检查，不向正式评测系统新增重型验收、巡检或自动修复。

## 2. GPT Live／Gemini Live 删除边界

### 2.1 Provider 范围

删除：

- `openai_live`：当前 GPT Live 前后台接入。
- `gemini`：当前 Gemini Live 接入。

保留：

- 普通 OpenAI Realtime 的 `openai`。
- 已迁移的 Qwen Adapter。
- 其他 Provider 的当前实现，本轮不顺带迁移或删除。

不为退役的两个 Provider 建立空 Adapter 目录。后续需要时，按统一接入规范重新新增完整实现。

### 2.2 移除新运行入口

从以下位置移除对应新运行支持：

- CLI Provider 可选项。
- 运行配置类型和校验。
- Provider 默认模型与推理参数表。
- `create_adapter()` 创建分支。
- 通用音频 Agent 中的对应类型、构造及 VAD 分支。
- `--live-config` 及 `live_config` 的新运行参数传递。
- Gemini 专属 VAD、推理或语言设置分支。

旧配置用于启动时明确拒绝，不回退到普通 OpenAI Realtime 或 Qwen。

如果删除字段会导致旧输入被配置模型静默忽略，应在配置加载入口保留简短的拒绝规则；不增加通用配置迁移或自动修复框架。

### 2.3 删除专属实现

主要范围：

```text
src/tau2/voice/audio_native/openai/live_adapter.py
src/tau2/voice/audio_native/openai/live_provider.py
src/tau2/voice/audio_native/gemini/
```

根据剩余调用方处理：

- OpenAI 公共事件、普通 Realtime adapter/provider 保留。
- 公共音频转换、异步循环、播放记录和 transcript 模型保留。
- LiveConfig 的提示词生成和运行逻辑删除。
- 若历史结果反序列化仍需要旧配置字段，只保留被动数据表示，不保留连接或执行能力。

不能按 `openai`、`live` 或 `gemini` 字符串全局删除代码；须区分专属实现、公共设施和历史名称。

### 2.4 脚本、测试和使用说明

- 删除只服务这两个接入的启动示例及专属测试。
- 混合测试文件仅移除相关用例，保留公共媒体和普通 OpenAI 测试。
- 当前支持列表不再列出这两个 Provider。
- 历史报告中的 Provider 名称、已保存分数和轨迹不批量替换或删除。

### 2.5 历史读取与恢复

历史结果读取和新运行配置分别处理：

- 历史结果可显示 `gemini`、`openai_live` 名称及已保存分数。
- 读取结果不能实例化已删除 Provider。
- 断点恢复需要重新启动已退役 Provider 时明确拒绝。
- 不为历史查看保留网络协议、连接客户端或提示词执行逻辑。
- 现有结果中如嵌入旧配置，允许以只读数据形式保留。

## 3. Gaia2 主入口旧领域残留清理

### 3.1 新运行入口与实际支持范围一致

优先删除明确不可达的内容：

- CLI 中已不支持的领域选项、帮助文字和运行示例。
- `retrieval_config`、`retrieval_config_kwargs` 等旧领域专属的新运行参数。
- Runner 中 knowledge／intake 等领域专属装配分支。
- 旧领域默认模型、提示词或配置注入。
- 无调用方的导入、辅助函数和测试目标。

同步检查相关批量运行、配置装配和 checkpoint 代码，避免参数虽然从 CLI 删除，却仍在内部被传递或隐式生效。

### 3.2 保留公共能力和历史字段

保留：

- 通用工具执行、消息、数据库及评分基础设施。
- 当前 Gaia2 实际使用的模型和辅助函数。
- 历史结果反序列化所需的数据字段。
- 有明确独立用途、且已与主入口隔离的模块。

例如历史 Info 中的 retrieval 字段可以作为旧数据继续读取，但新 RunConfig 不再允许它控制运行。

### 3.3 独立目录处理

对 knowledge、gym、api_service 等目录，先核对实际调用关系：

- 只有废弃入口且无当前调用方的部分，可连同专属代码删除。
- 仍有独立用途的模块，从 Gaia2 主入口隔离，不仅凭目录名整块删除。
- 不顺便重写这些独立系统或迁移它们的数据。

### 3.4 Leaderboard 等外围入口

区分当前运行与历史展示：

- 若旧领域 leaderboard 仅用于历史榜单展示，应明确标记历史用途。
- 删除失效的新运行入口和误导性的使用说明。
- 不把旧榜单 domain 字面量直接改为 Gaia2，伪装成已完成适配。
- 不调整当前指标统计公式，本轮错误、重试和统计口径工作仍暂缓。

这些是该修复产物的历史记录，实施时读取指定产物确认，不重新启动全量模型修复。

当前基础验证主要检查模型加载、数量、来源关系和部分依赖目标，不等同于全部参考执行和评分语义正确。

### 5.2 确认源版本是否匹配

对比修复 manifest 的源文件哈希与当前活动数据：

- 匹配时沿用已有变化记录。
- 不匹配时，按任务 ID、已有差异和源版本识别冲突。
- 保留修复期间已经产生的新修改，不直接覆盖。
- 不因为发现源版本变化就重新生成全部答案。
- 只读取本次指定输入和输出，不扫描整个归档目录。

### 5.3 明确集合与发布状态

沿用现有发布清单表达：

- base800。
- mind_change100。
- repetition100。
- AddTask100、Modify50、Cancel50。
- hidden100 独立集合。

代码清理不自动把 draft 改为 released。

未解决题目保留原内容和未解决状态，不根据猜测修改，不静默剔除后改变样本量。发布说明应如实记录该修订的实际处理与验证范围。

### 5.4 处理来源传播

- 基础题修复与 mind_change／repetition 的来源关系对应，同时保留各变体自身条件。
- AddTask／Modify／Cancel 保留自己的业务变化及专属参考内容。
- 交互变体 source hash 对应最终采用的源任务。
- 隐藏信息集合单独确认是否绑定变化后的源版本；如继续绑定旧版本，应明确记录，不顺便重做隐藏任务。
- 不通过修改 ID 或删除 provenance 掩盖版本冲突。

### 5.5 必要离线确认

复用已有基础验证，只补充：

- 文件可加载，任务身份和集合成员关系正确。
- 变体能够根据最终源任务构造运行视图。
- 对不同修改类型选少量代表题确认参考行为。
- 某个样例暴露问题时，仅扩展到同类修改或具体受影响题目。

不对每道题追加模型裁判，不全量重跑 1200 道，不自动循环修复直到“全部通过”。

验证结论保留具体范围：结构通过、代表样例通过、尚未执行的项目分别说明。

### 5.6 形成数据修订与活动入口

- 最终采用的数据和变化说明形成新的 revision。
- 正式活动入口保持唯一且明确。
- 原始来源、修复候选和未解决记录作为离线材料保留。
- 更新已有 manifest、源文件哈希和相关版本引用。
- 记录数据修复来源及本次实际验证范围。

运行时封存使用项目已有流程，不把当前代码哈希直接填入数据并沿用旧 verified 状态来声称已验证。

如果必要的封存或发布条件尚未满足，应保持候选状态并报告具体缺口，不以绕过校验完成发布。清理代码不引入另一套封存或验收系统。

## 6. 正式评测中的机制边界

正式运行只保留必要行为：

- 配置加载时拒绝已删除 Provider 和旧领域设置。
- Factory 只构造当前有效实现。
- 历史结果通过被动数据结构读取。
- Manifest 明确选择任务集合和数据修订。

不加入：

- 启动时遍历旧代码和整个归档。
- 每次运行对题库做依赖审计。
- 自动修复旧配置或任务。
- 每次评分重跑参考修复流程。
- 额外模型裁判、后台巡检或多层验收状态。
- 与暂缓事项相关的重试或统计规则改动。

删除正确性主要由依赖断开、入口收敛和明确的数据版本关系保证。

## 7. 推荐实施顺序

### 单元一：移除未完成的 Provider

1. 删除新运行配置和创建入口。
2. 删除专属实现及测试。
3. 保留普通 OpenAI Realtime 和公共媒体设施。
4. 保留历史读取，拒绝旧 Provider 恢复运行。
5. 更新当前支持列表。

### 单元二：清理旧领域残留

1. 清理 CLI 和新运行配置中的旧领域参数。
2. 移除不可达装配分支及无用导入。
3. 保留历史结果数据字段。
4. 按剩余依赖处理外围模块及旧脚本。
5. 更新失效命令和示例。

### 单元三：统一整理状态文档

1. 将讨论稿改成当前状态清单。
2. 更新数据量、指标与 Adapter 状态。
3. 链接权威文档，减少重复说明。
4. 明确两项暂缓范围和发布待决事项。

### 单元四：数据版本对齐

1. 读取已有修复产物和变化记录。
2. 对齐源版本与当前活动数据，处理具体冲突。
3. 确认基础题、交互变体、隐藏信息的来源关系。
4. 做必要结构确认和少量代表样例验证。
5. 形成明确 revision，更新清单及实际状态。
6. 如正式封存尚未完成，保留候选状态并列明剩余事项。

## 8. 轻量验证范围

1. 已删除 Provider 和旧领域配置不能启动。

3. 历史 GPT Live／Gemini 结果可加载；恢复运行明确拒绝。
