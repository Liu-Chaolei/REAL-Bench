# 统一发声判定与音频时间记录实施计划

状态：已实施。任务调度保留 TICK；公共播放时间线、用户已知发言范围与 Agent 发声检测已接入框架和两套指标。

本次落地采用 **20 毫秒 RMS 窗口，默认阈值为 PCM16 RMS > 0**，沿用最初希望参考的千问判定条件。阈值集中在 `src/tau2/config.py`，可通过 `TAU2_AUDIO_ACTIVITY_RMS_THRESHOLD` 对整次运行统一设置；没有按 Provider 单独调节，也没有使用转写模块阈值。

RMS 记录的是超过阈值的声音能量，默认值会把低幅噪声也算入。这是所选判定方式的含义，不增加语义识别人声模块。后续如需调整阈值，应统一调整并保留配置版本。

## 1. 本次目标

统一评测框架观察所有待测 Audio Agent 的方式，并使声音时间记录脱离 200 毫秒 TICK 的计量限制。

双方采用不同的信息来源：

- **用户侧：**模拟器知道自己安排了哪段发言、什么时候实际送入、送了多久，直接记录发言范围，不再用 RMS 或 VAD 猜测结束。
- **Agent 侧：**公共适配层根据实际播放音频，以统一方法检测发声位置。

音频的接收、送入、播放与停止在事件发生处记录时间。TICK 可以继续组织任务推进和兼容旧接口，但不能决定声音时间戳的精度，也不能成为音频收发与取消处理必须等待的边界。

本次先完成声音证据统一，再让现有指标使用这些证据；暂不合并两套指标公式。

后续的两套指标公式合并已经完成，当前口径见 [语音交互指标合并计划](voice-interaction-metrics-unification-plan.md)。本文件保留声音检测阶段的实施范围。

## 2. 已确定的范围

| 事项 | 实施要求 |
| --- | --- |
| 用户发言时间 | 使用模拟器已知发言范围与实际送入记录 |
| Agent 发声时间 | 使用公共音频检测结果，不采信各 Provider 自行给出的发声标记作为最终依据 |
| 时间来源 | 在公共音频收发、播放、停止位置记录，共用一个本地单调时钟 |
| 检测窗口 | 方案默认按 20 毫秒窗口、20 毫秒步长设计；这不是音频检测的物理下限 |
| `contains_speech` | 替换评测框架内的分散判定；需要精确时间的地方直接读区间或事件 |
| 待测 Agent 内部 | 不修改其内部声音检测、接话、生成和打断策略 |
| 两套指标 | 保留各自公式与统计口径，先统一声音及时间来源 |
| 验证 | 少量本地开发测试，不增加评测运行时验收机制 |

这次不恢复已经删除的指标，不修改整题成功公式，不调整数据集，不增加新的性能评分。

## 3. 当前实现的问题

### 3.1 声音被组织成固定 TICK

现有公共适配器每轮收发音频，把 Agent 输出限制为一个 TICK 的长度：超过的缓存到下一轮，不足的补静音。

`TickResult.get_played_agent_audio()` 当前对普通的不足一轮音频，假设音频从 TICK 开头开始，后面补静音。它尚未根据真实开始位置在前面补静音。

因此，事后把保存音频切成 20 毫秒窗口，并不一定能够恢复真正的发声起点。检测分辨率变小，不能修复已经丢失的时间位置。

### 3.2 运行时间和音频时间依赖事后映射

目前会记录一轮运行前后的单调时钟时间，同时把音频按 TICK 累积到媒体时间线上。部分其他事件通过区间插值映射到媒体时间。

这种记录不能替代逐段音频的真实接收、送入和播放记录。新声音时间线不应把一段运行耗时按比例压缩或拉伸成固定 200 毫秒。

### 3.3 发声判断有多个来源

千问当前用于发声标记的是整段播放音频 RMS 大于 0，媒体版使用 20 毫秒 WebRTC VAD，其他路径还可能使用 Provider 标记或音频非空判断。

千问转写模块的 RMS 阈值、静音等待和切句参数，是另一套用途，不能直接当成公共检测参数。

### 3.4 布尔标记还参与对话控制

`contains_speech` 不仅用于指标，也用于框架里的静音计时、用户模拟器接话和部分运行状态判断。本次需要统一这些外部观察来源，而不只是更换报表输入。

## 4. 目标处理流程

```text
用户模拟器
  └─ 发言音频与发言 ID
       └─ 公共输入发送过程：记录实际送入范围
            └─ 用户发言开始、结束或中途停止事件

待测 Agent
  └─ Provider 协议适配：持续接收音频并记录接收时间
       └─ 公共播放队列：记录实际播放、等待与取消
            └─ 公共声音检测：处理实际播放音频
                 └─ Agent 发声区间与当前发声状态

双方事件及区间
  ├─ 评测框架的接话、静音等外部观察
  ├─ 必要的 contains_speech 兼容输出
  ├─ 现有两套语音指标
  └─ 音频与评测日志
```

公共层负责可观察的音频行为，Provider 负责协议差异。检测模块不负责判断回答是否完成、任务是否成功，也不因检测到用户开口就自动替 Agent 停止输出。

## 5. 时间记录机制

### 5.1 明确三个时间

| 时间 | 含义 | 用途 |
| --- | --- | --- |
| 音频接收时间 | 评测端收到 Agent 音频包的时间 | 记录传输与排队过程 |
| 音频播放时间 | 公共播放端开始呈现这段音频的时间 | 计算用户可听到的响应与重叠 |
| 有效发声时间 | 播放时间加上检测出的音频内部偏移 | 指标使用的 Agent 声音边界 |

远端 Agent 的内部生成或发送时间，不一定能取得，也不一定与评测端时钟一致。本次不要求远端时钟同步，不把远端生成时间冒充本地播放时间。

这里的播放指评测端明确规定的播放过程，可以是按实时速度运行的模拟播放，不宣称测量真实扬声器的物理发声时间。

### 5.2 音频采样位置映射到播放时间

在一段连续播放的音频内：

```text
发声时间 = 这段音频的实际播放起点 + 发声采样位置 / 采样率
```

如果发生排队、断流、暂停或取消，按实际播放的分段记录处理，不能把这些空隙拼接消失。

示例：音频在 10.123 秒收到，10.140 秒开始播放，前 60 毫秒为静音，则声音起点是 10.200 秒，而不是接收时间或 TICK 起点。

### 5.3 在事件发生处记录

- 接收时间在接收回调中记录，不能等 TICK 结束后取队列时才记录。
- 用户送入时间在公共发送过程记录，表示评测端发送进度，不冒充远端已收到的确认。
- 播放时间由公共播放队列记录，不根据音频包到达时间简单推断。
- 取消时记录已播放到的采样位置，丢弃部分不得继续进入声音证据。
- 使用同一个本地单调时钟，相对本次运行起点保存秒数，避免墙上时间调整影响时差。

记录最少必要信息即可：角色、音频位置与格式、时间范围、发言或响应 ID，以及停止原因（如适用）。复用现有记录结构，不新建通用事件平台。

## 6. 用户侧：直接记录已知发言范围

### 6.1 正常完整发言

模拟器给每次发言关联已有的发言 ID，并保留对应音频范围。开始实际送入时记录开始；最后一段发言音频送完时记录结束。

连续完整送出的情况下：

```text
用户发言结束 = 实际送入起点 + 发言音频时长
```

若中途有真实发送空隙或停止，使用实际进度记录，不继续套用预计结束时间。

### 6.2 不重新猜测句末

采用用户已明确的定义：这次发言音频送完就是这次发言结束。不额外运行 VAD 寻找最后一个字，也不设置“静音多少毫秒就代表说完”的通用阈值。

同一次发言内的停顿仍属于这次发言。合成文件自身的尾部静音按当前发言音频定义保留，本次不引入自动裁剪；为了填满 TICK 额外加入的静音、发言之外持续播放的背景声不延长发言。

### 6.3 保留现有事件分类

附和、口头语、非定向讲话等继续使用模拟器已有的类型信息。背景噪声不能把用户标记成一直在发言。

用户“正在发言”的状态由实际送入的发言范围产生。该状态表达已知发言进度，不声称识别了每个字之间的声学静音。

## 7. Agent 侧：统一声音检测

### 7.1 公共模块职责

建议在 `src/tau2/voice/` 下增加小型公共模块，例如 `audio_activity.py`，负责：

1. 处理统一幅值表示的音频。
2. 跨网络包保存剩余采样，按固定窗口检测。
3. 输出相对于音频采样位置的有声区间及状态变化。

播放时间映射由公共媒体记录承担。不要让检测模块同时管理 Provider 连接、任务状态或指标公式。

### 7.2 窗口与跨包状态

默认采用 20 毫秒窗口、20 毫秒步长。网络包可以是任意长度：不足一个窗口的内容保留，和后续连续音频一起处理。

窗口边界不随网络包、TICK 或响应文本碎片重新起算。同一连续音频拆成不同大小的包，应该得到相同结果。真正的时间断点需要显式结束当前连续段，不能把空隙两边的采样拼成一个窗口。

流末不足一个窗口的部分按选定算法完成收尾，保留真实长度；内部补齐不得把发声结束延伸到实际音频之外。

### 7.3 格式和配置统一

统一解码、声道处理和幅值单位；若采用重采样，使用保留跨包状态的公共路径。不得对每个 Provider 设置不同检测阈值或单独自动放大音量。

检测方法与参数集中配置，在线观察和离线重算调用同一实现。日志记录一次方法、窗口、阈值和版本即可，不把它们变成新的 Agent 性能分数。

### 7.4 只检测，不猜回答完成

输出原始有声区间。短暂停顿可以把声音分成两段，但不能据此宣布整个回答完成，也不填平这些静音后再计算实际重叠。

如果后续指标需要把多段声音归为同一次发言，应在指标层单独定义，本次不增加语义句末判断。

20 毫秒窗口只代表检测分辨率；算法误判、缓冲和事件记录也影响误差，不能承诺所有时间误差都小于 20 毫秒。

## 8. 音频运行与 TICK 的关系

持续接收、输入发送、播放推进与取消处理不能必须等下一个 200 毫秒 TICK。

优先复用现有后台事件循环与流式队列，把仍在 TICK 结束处集中处理的音频工作移到公共媒体路径。无需另外重写整个任务调度器，也不增加第二套重复的后台线程体系。

TICK 保留以下职责：

- 推进现有任务、环境和非音频逻辑。
- 读取媒体路径已经产生的事件和状态。
- 为旧日志或接口提供按 TICK 截取的视图。

如果某个框架控制动作仍按 TICK 执行，其真实等待必须保留，不能在指标中减掉。需要立即作用于播放的取消动作走媒体路径；用户模拟器接话等其他调度逻辑本次不顺带整体重写。

不得通过把 TICK 从 200 毫秒简单缩小到 20 毫秒替代此次机制调整。

## 9. `contains_speech` 与框架行为

统一外部观察来源：

- 用户侧来自已知发言的实际送入状态。
- Agent 侧来自公共音频检测结果。
- 精确计时使用区间和事件，不从一个布尔值反推起止位置。

需要旧 TICK 布尔接口时，为该 TICK 生成是否与相应发言或声音区间有交集的视图。需要“此刻是否在发声”的控制逻辑，则读取当前状态，不能把“TICK 内任何时候发过声”等同于“现在仍在说话”。

梳理并替换评测框架内用于接话、静音计时、对话状态、指标和显示的分散判断。外部框架行为可能因此变化，这是统一观察机制的一部分。

保留待测 Agent 内部自己的 VAD、接话、生成和取消策略。Provider 的内部事件可以留作日志，但不覆盖公共检测结果。

## 10. 打断和播放取消

用户开始发言时，公共层记录用户事件并正常发送音频，不因为检测到用户发言就自动清空 Agent 输出。

待测 Agent 或现有协议产生取消请求后，由公共播放端执行，并记录已播放部分及剩余丢弃部分。保留响应 ID 对应关系，避免取消旧响应时误删新响应。

已播放的残余声音仍参与重叠和停止时间计算。收到但没有播放的内容不参与声音指标，也不当成用户听到的回应。

## 11. 现有指标与日志接入

### 11.1 本次统一输入，不合并公式

响应延迟、响应率、让话率、停止延迟、Agent 打断率、重叠时长、On Time Rate，以及 selectivity 三个细分指标，逐步改用共同的声音证据和时间记录。

具体保留规则：

- 各自原有的分母、响应范围、及时范围和统计对象保留。
- 原来以 TICK 数表达的时间阈值，按原有时长含义转换，不顺带改宽松程度。
- 不将两个同名指标直接合并或更换成另一版公式。
- selectivity 的事件类型仍来自模拟器标签，公共声音检测只提供 Agent 发声和停止信息。
- 不改其他非语音指标的题目等权汇总原则。

### 11.2 在线与离线共用实现

在线框架观察与离线声音重算使用同一个检测模块及配置。保存实际音频分段与时间记录，避免离线把播放空隙消除，或重新按 TICK 假设起点。

新记录携带必要版本信息。已有历史数据保持原样，不批量重跑、不声称旧 TICK 音频能恢复已经丢失的细粒度时间。保留现有历史读取路径，具体历史兼容代码按必要范围调整。

缺失信息继续沿用既有日志和不可用表示，不补造时间，不以旧 Provider 标记悄悄代替新结果。本次不重新制定“评测无效还是 Agent 失败”的完整规则。

## 13. 实施顺序

### 第一步：确定检测配置并梳理公共接入点

明确 Agent 侧的检测方法及参数。沿现有 Provider 路径定位接收、播放、取消位置，复用已有后台运行机制。确认待测 Agent 内部逻辑与评测框架外部观察的边界。

产出：小范围的数据与接口约定，不建设通用插件系统。

### 第二步：实现独立媒体时间记录和播放进度

把接收时间记录放到接收位置，把播放起点与停止位置交给公共播放队列。保留真实排队、空隙、取消和采样进度。使必要音频收发及取消处理脱离 TICK 等待。

产出：可信的音频事件时间线；旧 TICK 输出成为视图。

### 第三步：接入用户已知发言事件

把发言 ID、音频范围和实际发送进度连接起来，记录正常结束及中途停止。背景声和 TICK 补齐静音不延长发言。

产出：无需声音检测的用户开始、结束信息。

### 第四步：实现 Agent 公共检测

完成格式统一、20 毫秒窗口、跨包缓存、连续段处理与采样区间输出。在线、离线调用同一个实现。

产出：所有 Provider 共用的 Agent 发声区间。

### 第五步：替换框架中的分散判定

更新 `contains_speech`、当前发声状态和精确时间的消费者，分别使用合适的信息。移除 Provider 对评测声音证据的覆盖，不改其内部策略。

产出：框架观察和指标采用同一声音事实。

### 第六步：接通日志与现有指标

保存直接时间记录，更新离线读取，切换两套指标的声音输入。保留公式、事件分类与既有阈值时长，不合并输出含义。

## 14. 轻量验证原则

仅用少量合成音频、假时钟和已有离线样例验证关键机制：

1. 同一段连续音频按不同网络包大小输入，检测区间一致。
2. 有前置静音的音频，能得到 TICK 内部的发声起点；播放起点位于 TICK 中间时不被提前。
3. 接收后排队播放的样例，接收时间与发声时间正确分开，真实空隙保留。
4. 用户发言内停顿不结束发言，发言送完或中途停止产生正确结束事件。
5. Agent 取消后，只保留已播放部分；取消旧响应不影响新响应。
6. 一组已知双方时间的样例，能为现有延迟和重叠计算提供正确输入。

优先扩展已有相关测试，不创建大规模测试矩阵。测试代码留在开发测试中，不进入评测系统主流程。

结果一致性主要通过公共检测实现、单一事件记录来源和明确的播放队列机制保证。
