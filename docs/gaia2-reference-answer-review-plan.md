# Gaia2 参考答案与交互变体离线审查计划

状态：审查工具已实现，材料已准备；DeepSeek 批量审查待配置 `DEEPSEEK_API_KEY` 后续跑。本计划用于审查数据和参考答案质量，不修改评测运行流程，也不把审查步骤加入正式评测系统。

## 1. 审查目标

检查每道题的用户要求、初始事实、参考操作、参数、依赖、参考回复和实际评分规则是否相互一致，并判断一个合理完成任务的 Agent 是否会被当前参考答案或评分规则误判。

审查从用户要求出发，再对照参考答案。参考答案可以被判定为错误、遗漏、不可执行、过度限制或证据不足；不能把参考答案默认当作正确标准。

审查采用 DeepSeek 进行大部分语义阅读和问题发现，程序负责数据整理、结构比较、事实提取、结果缓存和必要的局部复现。两者各自承担清晰的职责：模型解释要求和指出冲突，程序提供可复现的证据。

## 2. 当前数据范围

活动数据目前包含：

| 数据集合 | 数量 | 本轮处理方式 |
| --- | ---: | --- |
| `base` 主任务 | 800 | 每道题完整审查三个阶段 |
| `repetition` | 100 | 参考内容与来源题一致，复用来源审查；检查请求差异 |
| `mind_change` | 100 | 参考内容与来源题一致，复用来源审查；检查请求差异 |
| AddTask | 100 | 复用来源题审查；独立检查追加请求、追加参考和 A+B 组合 |
| Modify | 50 | 复用来源题审查；独立检查修改前后请求、任务绑定和运行语义 |
| Cancel | 50 | 复用来源题审查；独立检查临时 B、取消对象和 A 的保留要求 |
| 静态 async 100 | 100 | 按当前决定停用，不纳入新的参考答案审查 |

加载后的正式任务规模为：

```text
800 + 100 + 100 + 100 + 50 + 50 = 1200
```

AddTask、Modify、Cancel 存在于独立的 `data/tau2/domains/gaia2/interaction_variants.json`，运行时从 200 个不同的 base 来源构造，不覆盖来源题。

已经确认的复用关系：100 道 repetition 和 100 道 mind change 的参考事件、环境事件、阶段检查、阶段评分条件、整题评分条件和初始快照，均与来源题相同。它们不重新审查整套参考答案。

静态 async 配置中的 100 道题暂时停止使用。本计划不花时间审查这套将被停用的静态配置；后续删除、归档和代码清理另行处理。

## 3. 800 道主任务的检查对象

每道题都以完整的三阶段为单位审查。单独查看某个工具调用或某一段请求不足以得出结论。

### 3.1 用户要求

检查三个阶段的请求以及它们之间的关系：

- 需要完成哪些业务目标；
- 哪些要求是条件分支、修改、取消、禁止或保留；
- 哪些对象、数量、时间、地点、文本和权限要求必须保留；
- 哪些内容是查询结果，哪些内容是实际写操作；
- 后续阶段是否依赖前一阶段产生的对象或结果；
- 用户是否明确要求了先后顺序，或者允许多种合理顺序。

### 3.2 初始事实和环境变化

从题目引用的 snapshot、文件和应用状态提取与任务有关的事实：

- 联系人、参与者、会话和已有消息；
- 日程、订单、收藏、房源和商品；
- 文件、目录和附件；
- 环境自动消息、取消、状态变化和触发条件；
- 查询题的完整候选范围及可复算结果。

对计数、排序、最低／最高、并列和筛选问题，不能只把参考答案中的数字提供给模型。材料应包含完整候选数据，或包含带字段来源和筛选过程的程序计算结果。

### 3.3 参考操作与参数

检查 `scenario.events` 中的 reference 事件：

- 操作是否覆盖用户真正要求的业务动作；
- 是否包含不必要、重复或不可执行的操作；
- 工具是否存在并能处理这些参数；
- 对象、ID、时间、数量、文本、成员和附件是否正确；
- 新建对象的后续操作是否引用前一步的实际结果；
- 是否把参考执行过程中随机生成的 ID 错误写成固定值；
- 参考回复是否误把查询、读取或环境事件当成 Agent 必须执行的写操作。

工具评分只把写操作放入 `tools`、`parameters`、`order`、`effects`；读操作和环境事件可以辅助解析，但不直接成为写操作评分项。审查材料仍保留它们，避免错误理解完整流程。

### 3.4 参考依赖、时间和阶段边界

检查 `dependencies`、结果引用、延迟和阶段关系：

- 操作本身必须依赖的前置操作是否存在；
- 用户明确要求的顺序是否被表达；
- 是否把参考作者选择的一种实现顺序误设成唯一允许顺序；
- 是否遗漏了用户明确表达的先后关系；
- 跨阶段是否错误引用了尚未生成或属于其他对象的结果；
- 读操作被排除出写操作评分时，是否仍正确传递必要的因果关系；
- 时间条件、环境触发和取消是否能在实际运行中成立。

程序应先做引用、循环、缺失事件和 ID 结构检查；模型再判断这些关系是否符合用户要求和工具实际能力。

### 3.5 参考回复与查询结果

检查参考回复事件、`communicate_info` 和阶段答案：

- 查询数字、名称、状态和对象是否能从完整初始事实复算；
- 回复是否遗漏用户要求报告的内容；
- 是否声称了尚未完成的操作；
- 是否泄露 Agent 不应知道的参考信息；
- 是否把环境消息、参考答案或未来状态当成用户已知事实；
- 同一业务结果是否被错误拆成不必要的多个回答要求。

回复正确性的最终指标另行设计；本轮只审查参考回复是否有事实、范围或阶段错误。

### 3.6 编制检查与实际评分规则

`scenario.stages[].checks` 是参考方案编制验证材料，不等于待测 Agent 运行时必然执行的 effects 检查。两者必须分开核对：

- 编制检查是否检查正确对象、正确阶段和正确时点；
- tools 是否只比较必要写操作；
- parameters 是否把合理表达误判成参数错误；
- order 是否遗漏必要关系或限制了不必要的顺序；
- effects 是否检查了操作后的实际状态；
- ENV Assertion 是否覆盖整题目标；
- 当前指标是否会放过明显错误或误判合理实现。

这项检查需要结合实际代码入口，不只读取题目里的检查字段。

## 4. 200 道请求变体的审查

这 200 道不重复审查来源题的参考操作。它们要审查的是：**改写后的请求是否仍然与沿用的参考答案一致。**

每道变体材料包含来源题三阶段请求、变体三阶段请求、变更字段、来源参考摘要和基础题审查结论。

### 4.1 Repetition 100

检查：

- 重复是否只是强调同一个要求；
- 是否误变成“再执行一次”；
- 重复内容是否改变数量、对象、范围或顺序；
- 跨阶段指代是否仍指向同一对象；
- 参考操作仍只需要执行一次是否合理。

### 4.2 Mind Change 100

检查：

- 用户最后确认的值是什么；
- 旧值是否被明确撤回；
- 没有撤回的要求是否继续有效；
- 参考参数是否使用最终值；
- 修改发生在相关操作之前还是之后，参考依赖是否仍成立；
- 动态表达是否保留了改主意的过程，而不是只留下最终一句话。

基础题参考有问题时，关联变体继承同一个问题；变体独有的请求差异另列。

## 5. AddTask、Modify、Cancel 200 道的审查

这 200 道的业务来源仍然是 800 道主任务，但它们在第三阶段增加了交互变化。当前数据标记为 `generated_draft`，表示已经生成和本地结构检查，不表示完成语义审查。

### 5.1 AddTask 100

语义是：

```text
原任务 A 已进入后台
→ 用户追加独立要求 B
→ A 和 B 同时继续有效
```

检查：

- B 是否真的是新增目标，而不是重复 A 或修改 A；
- B 的对象、参数、时间、内容和禁止事项是否明确；
- B 的新增 reference events 是否完整、可执行、参数正确；
- A、B 之间是否错误添加了固定的整体顺序或并行要求；
- B 是否依赖 A 尚未产生的结果；
- 新增参考答案是否准确描述 B 的结果；
- A 原有参考目标与 B 是否冲突；
- 加载后的任务和评分入口是否确实包含新增参考。

AddTask 的新参考事件独立审查；来源题的参考审查可以复用。

### 5.2 Modify 50

语义是：

```text
先提出临时要求
→ 后续修改同一项任务的某个要素
→ 其余要求继续有效
```

检查：

- 临时要求是否完整且可执行；
- 后续请求是否明确指出修改对象；
- 修改的参数是否确实变化；
- 未修改的要求是否保留；
- 修改前已经合法执行的部分是否不被错误判为失败；
- 任务 ID、绑定和修改操作是否指向同一后台任务；
- 当前只判断原生 modify 接受结果的评分是否与数据语义一致。

Modify 当前跳过原 ENV、执行质量和状态交互评分，所以审查重点是变体数据、后台绑定和 native modify 评分，不把原参考操作路径当成这个变体的硬标准。

### 5.3 Cancel 50

语义是：

```text
原任务 A 继续
→ 增加临时任务 B
→ 用户取消 B
→ A 保留，B 的剩余工作停止
```

检查：

- B 是否与 A 清楚区分；
- 取消话语是否指向 B；
- 是否把已完成结果错误地要求撤回；
- A 是否被错误停止；
- B 在取消前已完成的部分如何处理；
- 任务状态已终止时，取消请求是否仍被生成或被错误计分；
- 当前 cancellation confirmation 评分是否只证明 B 被取消，而没有把 A 的成功误当成 B 的成功。

Cancel 当前跳过原 ENV、执行质量和状态交互评分，审查重点是任务绑定、取消时机、剩余工作和 native cancel 评分。

## 6. 动态异步交互的审查

静态 async 100 配置按已确定方向停用，不进入本轮逐题内容审查。这里的“动态异步”指运行时根据真实后台观察选择并生成请求的机制，以及 AddTask、Modify、Cancel 的动态管理运行。

### 6.1 机制级检查

程序读取配置和代码，列出实际启用的：

- 状态：queued、waiting、running、completed、failed、cancelled；
- 操作：query、result、modify、cancel；
- fallback 关系；
- 最小观察数、最小停留时间、转折次数、最长等待时间；
- 语言模板、LLM 生成设置和回退模板；
- 任务绑定规则、任务 ID 优先级和文字提示后备匹配；
- 结果和回复的评分条件。

随后由 DeepSeek 审查这些机制是否允许：

- 生成请求与选定任务一致；
- 查询状态与实际状态一致；
- result 只在结果可用时提出；
- modify 明确包含修改内容；
- cancel 只取消目标临时任务；
- 状态竞争、任务完成、取消和修改失败时没有错误归因。

### 6.2 实例级检查

每条已有运行记录提供完整链：

```text
实际后台任务
→ 观察到的状态和时间
→ 选定意图
→ 生成请求及来源（LLM 或模板）
→ 实际发送时间
→ Agent 操作和返回
→ Agent 回复
→ 当前 native_result_reward / reply_reward
```

重点覆盖 running 查询、完成后取结果、失败任务、多个并行任务、取消竞态和修改后状态变化。没有真实记录的分支，只用明确标记的离线状态序列检查机制，不把模拟结果称为 Agent 表现。

### 6.3 动态生成内容的检查

DeepSeek 检查生成文本是否：

- 没有泄露内部任务 ID；
- 没有声称尚未发生的完成或失败；
- 没有改变状态或操作类型；
- 没有新增业务目标；
- 对 Modify／Cancel 保留原任务语义；
- 使用了用户能理解的任务指代；
- 与选中的任务和实际观察时间一致。

模型无法验证的任务关联、状态和操作结果，交给程序从事件时间、任务 ID 和返回结果核对。

## 7. 审查材料包

每道 800 主任务建立一个材料包：

- 三阶段请求和用户事件；
- 相关初始快照、文件、联系人、日程、消息、房源、商品及完整候选数据；
- 环境事件和触发条件；
- 全部 reference／user／environment／agent 事件；
- 参考参数、结果引用和依赖图；
- 参考回复、`communicate_info` 和阶段 checks；
- 实际 `tools`、`parameters`、`order`、`effects`、ENV 入口及适用性；
- 来源题、变体和异步关联关系。

提供给模型的内容要明确标注“待审查参考”，避免把参考答案写成事实。超过上下文限制时，按应用和问题拆分，保留字段来源和可复算结果。

## 8. DeepSeek 调用方案

项目已有 DeepSeek 兼容配置和可缓存的 JSON 请求封装，审查可以复用，但使用独立的离线配置文件，不混入正式评测配置。

建议每道主任务至少两轮：

### 第一轮：不看参考答案的需求理解

输入用户请求和必要事实，要求输出：

- 各阶段业务目标；
- 必须操作、可选操作和禁止操作；
- 必要对象、参数和结果；
- 用户明确要求的顺序；
- 可以自由变化的顺序或实现路径；
- 查询题的可复算结果；
- 缺少的事实和疑点。

### 第二轮：对照参考与评分规则

补充参考操作、参数、依赖、回复、checks 和实际评分代码说明，要求输出：

- 参考操作是否完整、必要和可执行；
- 参数和对象引用是否正确；
- 依赖是否缺失或过度限制；
- 参考答案是否有事实错误；
- checks 是否验证了正确对象和阶段；
- 评分是否会放过错误解或误判合理解；
- 每个问题的证据、影响和建议修复层级。

模型可以提出未预设的新问题类别，不能只输出通过／失败。

变体不重新做第一轮基础题审查。Repetition、Mind Change、AddTask、Modify、Cancel 使用各自的差异输入和来源结论，调用量按差异复杂度安排。

JSON 输出使用项目现有 `TauJsonModel`，保存原始返回、提示、schema、模型、用量、成本和结果哈希。DeepSeek 官方 JSON Output 要求请求声明 `response_format: {"type":"json_object"}`、提示包含 JSON 要求，并设置足够的输出长度；因此审查 schema 和 prompt 要符合这些条件。[官方 JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)

官方支持 OpenAI 兼容 Responses API；现有项目也支持 OpenAI 兼容网关。正式执行前固定一个 API 入口和模型，不在批处理中混用直连和网关。[官方 Responses API 说明](https://api-docs.deepseek.com/guides/responses_api/)

并发先从 2～4 开始，按实际网关限额调整。官方对账户级并发和 429 有明确限制，客户端需要有限重试、断点续跑和失败记录。[官方限流说明](https://api-docs.deepseek.com/quick_start/rate_limit/)

## 9. 审查产物

独立审查目录建议为：

```text
gaia2-reference-review/
├── config.yaml
├── inventory.json
├── inputs/
├── responses/
├── findings.jsonl
├── progress.jsonl
└── report.md
```

每条问题至少包含：

- 题号、阶段、变体类型；
- 涉及的事件、参数、依赖或评分入口；
- 用户原文依据；
- 参考内容；
- 初始事实或代码依据；
- 具体冲突与影响；
- `confirmed`、`needs_evidence`、`no_issue` 或 `incomplete` 状态；
- 建议修复层级：数据、参考操作、依赖、动态机制、评分规则或文档。

已有模型生成审核记录只作为证据，不直接修改题目。

## 10. 执行顺序

1. 建立 800 主任务索引、200 变体来源关系和动态交互机制索引。
2. 生成材料包字段映射，确认初始事实和查询计算可以复现。
3. 先用少量真实题目测试 DeepSeek 提示、输出 schema、上下文长度和成本；这些题属于正式审查，不作为唯一代表样本。
4. 持续逐题审查 800 道，不因程序结构检查通过而跳过语义审查。
5. 审查 repetition 和 mind change 的请求差异。
6. 审查 AddTask 追加目标及其新增参考；审查 Modify 和 Cancel 的交互语义、绑定和评分。
7. 审查动态异步机制及已有或离线构造的状态案例。
8. 对需要事实确认的问题做局部程序复现，不默认执行完整 Agent 测试。
9. 汇总问题、合并同一公共根因的影响范围，再决定修复批次。

## 11. 轻量边界

本计划是离线数据质量审查：

- 不在正式评测启动或运行时调用审查模型；
- 不增加每道题运行前后的验收流程；
- 不自动修改题目、参考答案或评分代码；
- 不因模型输出“通过”就跳过程序证据；
- 不要求在审查期间重跑完整 1200 道 Agent 评测；
- 不把局部参考执行结果当成全量正确性证明。

审查结果先汇报，再由人决定哪些问题需要修改。回复正确性和新的整体完成指标继续按此前约定单独设计，不在本轮偷偷改变定义。
