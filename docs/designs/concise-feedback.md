# 精简反馈评测：实现规划

> 历史设计说明：下文记录 `/1` 设计。当前 `/2` 已按 [反馈指标收拢计划](../feedback-score-simplification-plan.md) 合并 raw/最终反馈分，删除独立真实性状态、重大错误清零和错误率统计；陈述真实性由 Grounding 负责。下文旧公式、字段和相关验证设想不再定义当前行为。中文与英文现有预算沿用各自配置，使用方式以 [当前说明](../concise-feedback.md) 为准。

状态：设计记录，2026-11-07。第一版离线实现已完成，使用方法及当前限制见 [精简反馈评测](../concise-feedback.md)。用户已基于中文示例选定初始预算 `10 + 20N`，记录为 `zh-feedback-user-initial-v1`；真实窗口人工复核、实际模型语义验收与留出听评验证尚未完成。下文包含后续验证目标，不代表这些目标已有实测成绩。

## 1. 目标与设计决策

评价 Agent 在实际执行结果下，是否用适当的篇幅向用户传达了必要的信息。成功、部分完成、失败、结果不确定和缺少用户输入均属于合法的评价情形。

采用 TREC information nuggets 的思想：评测时建立信息点、匹配实际回答、按去重后的有效信息量给予长度预算。本文是针对交互式 Agent 的新设计，不声称复现原始 TREC 分数。原始来源为 [TREC 2004 QA overview §2.3](https://trec.nist.gov/pubs/trec13/papers/QA.OVERVIEW.pdf)。

第一版决策：

- 新增可选 measure `conciseness`，独立版本 `tau-feedback-conciseness/1`。
- 离线读取已保存的实际送达文本和执行证据，不重跑 Agent、用户或业务工具。
- 两阶段 LLM：先独立建立反馈信息点清单，再冻结清单、对齐待测回复；数值由程序计算。
- 请求窗口为最小计分单位，trial 为主汇总单位；Gaia2 第一版复用实际送达的 scenario stages。
- 覆盖率和长度效率是主要可解释结果；另输出候选综合分 F3 和真实性状态，经人工验证后才能作为正式排名依据。
- 使用文本长度作为第一版效率分母，音频实际播放时长作为独立辅助数据，避免把语速直接当成表达精简性。
- 与任务 reward、intent、execution、real_voice 和规划中的 interaction 分开，任务失败不自动令沟通分为零，沟通分不能补偿任务失败。
- 不要求后台任务边界，因此不依赖 Qwen BackendInput。第一批支持已有完整 Gaia2 diagnostics evidence；其他域通过相同证据契约扩展。

## 2. 已有能力与需要补齐的证据

已有 `DiagnosticEvidence` 提供：

- `user_inputs`：实际送达的用户发言和 Agent 发言，稳定 ID、阶段、起止位置、完整性；Agent 使用 `assistant_context` role。
- `operations`：工具名称、实参、结果、错误、调用开始/完成时间、前后状态帧。
- `frames`：执行中捕获的状态，而不是离线重建的猜测状态。
- `stages`：真实请求开始、送达完成和阶段信息。
- `audio`：实际交付的音频、媒体 timeline，以及存在时的单调时钟映射。
- `source` / `errors` / `complete`：来源、终止原因和采集限制。

现有收集器不能保证每条 Agent transcript 都有词级音频对齐，也没有通用字段证明后台结果何时送达前台。不能把工具在环境中成功，直接当成前台已经知道成功。

新增评测必须派生并保存每个来源的 `evidence_availability` 和 `time_basis`。不为评分伪造前台交付事件、时间映射或丢失的文本。可靠的状态/结果可判定真实业务状态；涉及 Agent 当时可知性或时间先后的结论，缺少证据时保持 unknown。

## 3. 请求窗口与评分范围

### 3.1 第一版边界

一个窗口从已送达的业务请求开始，到下一个业务阶段开始或通话结束为止。窗口由程序根据已保存的 stage delivery record 确定，不让 Judge 任意分段。没有 stage 且只有一个可确认业务请求的运行使用整通窗口；多个业务请求无法可靠分界时标记 `unsupported_request_boundaries`，不能默认为一个任务。

- 场景中未发布的请求不评价、不生成要点，另外报告 stage coverage。
- 请求部分送达：只使用能够验证实际送达的部分；完整要求不可恢复时该窗口 unavailable。
- 用户在窗口内的追问、澄清和修改保留原文，按时间生效，不自动增加一个新的基础长度预算。
- 用户明确增加新的业务目标但没有可靠阶段边界时，第一版不自动让 LLM 创建新窗口；保留为范围限制或 unavailable。
- 一个 Agent 发言跨越边界，能够可靠切分已送达文本时切分；不能切分则相关窗口不可精确评分，不能按时间比例分配文字。
- 请求覆盖的具体用户发言 ID、Agent 发言 ID、边界依据落盘，确保不丢字、不重复计字。

### 3.2 计入哪些 Agent 内容

第一版按请求窗口内实际送达的全部 Agent 文本计算长度，包括结果、错误反馈、必要澄清、确认、进度播报和重复回复。这样不会因为 Agent 把长答案拆成多段，就躲过长度惩罚。

基础预算容纳短开场和衔接；由用户追问或真实信息缺口产生的必要沟通，可形成有限的反馈要点。纯礼貌表达不逐条生成信息点，泛化的“正在处理”不因重复出现获得额外预算。

这是一项请求范围内的沟通效率指标，不能将每个低信息量交互直接判成无效。`interaction` 负责有效性；本指标负责整体覆盖与长度成本。首批人工验证必须专门检查必要等待播报是否受到过度惩罚。

### 3.3 状态和时间

窗口终点的状态用于确定最终应反馈的结果；不能用后续阶段的结果满足本窗口要求。请求取消或修改时，保留需要解释的已发生效果，但不要求继续报告已被撤销的未来目标。

第一版两次模型调用都只读取当前窗口及必要历史，不读取后续阶段。窗口内仍然是 batch 评测：第二阶段会看到窗口内未来事件，标记 `evaluation_mode=request_window_batch`、`future_context_visible_within_window=true`。证据时间引用校验能发现明显违规，不能宣称完全消除 Judge 的未来信息偏差。

实际工具时间、媒体相对秒、文本消息序号不可直接混排。复用已有单调时钟映射；缺少映射时只能进行可证明的偏序判断，不能据数值大小猜测先后。

## 4. 第一阶段：独立生成反馈信息点

### 4.1 输入隔离

输入只含：

1. 当前窗口真实用户要求及其补充、撤销、状态追问。
2. 必要历史：用户已确认的约束，以及上一窗口已验证的结果/已匹配信息点。
3. 工具返回、执行错误、相关状态变化及完整性说明。
4. 若涉及必须确认、限制或拒绝，提供运行时归档的相关政策/工具契约。
5. 固定的生成 rubric、原子化规则、输出 schema。

当前窗口待测 Agent 的回复文本不进入第一阶段。历史 Agent 陈述只能作为待核实的“此前已告知”线索，不能作为业务真值或新增用户要求。首批实现默认使用已验证的历史匹配记录；无法验证的历史内容明确标记，不借此免除本窗口的必要要点。

不输入原 reward、其他 Judge 分数、参考工具轨迹、未送达的隐藏用户脚本。`communicate_info` 不直接导入为本次反馈清单；需要从真实运行证据建立清单，避免重新退回固定成功答案。

查询的精确答案有时需要从已取得的工具结果做求和、筛选或日期运算。可支持的简单计算由程序执行并保留输入和计算规则；不重跑业务工具。LLM 无法核实的计算不能变成确定的目标事实。正确答案验证能力不足时，报告 evidence incomplete，而不是认可 Agent 自己提供的数值。

### 4.2 结果状态

状态可按子目标区分，整个请求的粗分类是：

| 状态 | 反馈要求 |
|---|---|
| `success` | 用户请求的结果，以及影响使用的必要限制/后续事项 |
| `partial_success` | 哪些已完成、哪些未完成，必要原因和有依据的下一步 |
| `failed_confirmed` | 明确未完成；仅在已知时说明原因；必要恢复方式 |
| `outcome_unknown` | 无法确认是否生效；不将超时等同于确定失败；可核实的下一步 |
| `blocked_on_user` | 缺少什么必要输入或授权，询问最少的相关信息 |
| `not_attempted` | 已有完整证据证明未执行时，如实说明未完成；不能虚构外部障碍 |
| `evidence_incomplete` | 不能可靠确定以上状态；不可将数据缺失视为模型没有执行 |

未观察到操作不自动等于未执行；需要操作日志完整性或其他肯定证据。工具返回成功也不总是业务效果成功，应遵守工具契约并优先使用可验证状态。

任务失败原因若属于模型本身，仍可评价其如实反馈，但必须与任务成功率并列；不允许只公布成功沟通的子集。

### 4.3 信息点字段

每点包含：

- `id`：程序分配的稳定 ID。
- `requirement_ids`：关联用户请求。
- `proposition`：需要表达的事实或必要沟通目的。
- `kind`：`result`、`status`、`reason`、`limitation`、`next_step`、`clarification`、`required_confirmation`。
- `necessity`：`required` 或 `optional`，并给一句必要性依据。
- `evidence_refs`：事件/状态路径 ID、原文或结构化值。
- `available_from`：可证明的最早可用位置，未知则 null。
- `scope`：对象、数值、单位、量词、时间、否定和适用阶段。
- `equivalence_group`：同义表述或可接受替代方式，只能获得一次预算。

不要求 Agent 使用指定措辞、复述操作过程或解释用户没有要求的推理。

### 4.4 原子化和相关性规则

- 一个信息点对应一个可以独立判断是否表达正确的用户所需命题；金额与币种、数值与单位不拆开。
- “两点的会议室没有订成”和“原因是没有空位”可以分开；“失败”“没成功”“未完成”不能拆成三个状态点。
- 日期、地点、对象等是否独立计点，取决于它们是否承载独立且必要的用户信息；不是按 JSON 字段机械计数。
- 用户要求名单时，根据固定 list-item 规则拆分，每个对象的指定属性捆绑，不能每个字或属性无限拆分；保留清单长度和复杂度类型用于校准。
- 操作步骤不自动成为输出要点；用户要求展示过程、审计记录或计算步骤时才纳入。
- 只有用户确实需要决策、使用结果或理解限制的信息才是 required。错误码、堆栈、内部 routing 等通常不属于必要反馈。
- 原因、替代选项和下一步均需证据。无法验证“可以重试成功”时，只能表达可尝试/待核实，不制造保证。
- optional 必须与当前要求直接相关。数据库中的其他正确事实不自动进入 optional。
- 用户主动要求重复时，可以重新形成沟通义务；无人要求且无变化的复述不增加信息点。
- 同一对话中基于用户明确追问产生的独立状态回答可以计点；Agent 自己产生更多播报不能增加预算。

第一阶段不得直接输出数值评分、自由长度预算、候选回答或从待测回复提炼的“最短答案”。

### 4.5 清单检查和冻结

程序验证 schema、来源 ID、阶段范围、类型和引用路径；合并完全相同的规范化命题，拒绝重复 ID。语义去重和必要性仍需模型规则与人工抽查，不能声称通过 schema 就保证语义正确。

来源缺失、必要事实冲突未解决、清单整体不可信时，标记 `nuggets_unavailable`，不调用第二阶段。存在未解决的必要义务时不能将其从分母悄悄删掉。

有效清单以 `nuggets_sha256` 冻结保存，第二阶段只能引用其中的 ID，不能增删或重写信息点。相同用户要求和相同规范化执行证据的清单可共享缓存；由于第一阶段不含待测回复，换一份回复应命中同一清单。

## 5. 第二阶段：回复对齐与真实性检查

### 5.1 输入与输出

输入是冻结清单、同一份执行证据、原始用户要求和带稳定 ID 的实际 Agent 发言。Judge 只输出判定与证据片段，不输出总分。

每个信息点恰好一行：

- `matched`：命题的对象、值、单位、条件和确定性正确表达。
- `missing`：没有表达或不完整到无法支持该命题。
- `contradicted`：表达了与该命题相反或错误的内容。
- `uncertain`：无法恢复文本、对齐、语义或时间关系。

同时列出有证据的：

- 同义重复，关联首次表达和重复原文。
- 无关或不可支持的业务陈述。
- 对业务结果、关键数值、授权、风险或下一步构成实质误导的陈述。
- 明确修正：后续正确更正可满足结果覆盖，但早先误导仍留下独立记录，不能被“曾说对一次”抹掉。

引用采用 `utterance_id` 加逐字连续原文，程序计算偏移；不存在或对不上的引用不能给匹配信用。无需把所有文本精确切成必要/冗余字符来计算主分，避免引入另一套高成本 span 标注。重复与无关定位仅用于解释和审计。

### 5.2 最终立场和时间规则

同一命题先错后明确更正，最终立场正确可以给 matched，并保留错误；先对后错且未修正为 contradicted；多个相互冲突结论没有解释时不能挑选正确的一句给满分。

未生效的操作提前宣称成功应记录为误导；最终后来成功不消除提前声称。只有实际时间和交付证据充分时才能作确定结论，时间不足为 uncertain。模型不能仅凭 Agent 使用完成时态证明成功。

首版口径已确认：窗口内出现任意 `complete=false` 的 Agent 发言时，跳过整个窗口，不恢复截断前缀；这不是首版待补功能。纯查询执行评分继续只检查完整交付的发言。不得拿未播出的文本、后台结果或完整 TTS 原稿补足回复。

### 5.3 判定失效

无效引用只将相关判定降为 uncertain，并记录原始标签。漏掉 required 行、重复 ID、试图修改清单、结构无法恢复属于 grader error，不能只挑合法行评分。

真实性只判断有证据的业务断言。礼貌语、一般衔接语不自动视为 hallucination；证据省略也不等于否定。

## 6. 纯程序评分

### 6.1 长度

`L` 为窗口内已送达 Agent 文本的 NFC 规范化非空白 Unicode 字符数。标点计入，保留所有业务文字、重复、礼貌语和填充语；只去掉项目确认的非口语控制标记。不能删除“无效文本”后再计分。

固定字符口径使程序容易复核，但不代表各语言天然可比；各语言分别校准预算。混合语言、代码、大量数字/长标识符必须单列，未校准的类别只报告覆盖和原始长度，不给正式效率分。后续若改成 tokenizer，必须单独版本化，不能在同一榜单混用。

### 6.2 必要信息覆盖率

设 required 总数为 G，正确覆盖数为 M，未知数为 U：

```text
R = M / G                        # U = 0
R_lower = M / G
R_upper = (M + U) / G             # U > 0 时 R = null
```

missing、contradicted 不给覆盖信用。第一版 required 等权，通过固定粒度避免任意权重；高风险误导另做真实性门控。

G=0 时不自动赋满分：检查是否属于不需反馈的情形、生成失败或需求证据不足；输出 not_applicable 或 unavailable。对一个已完整送达且需要结果的请求，即使未执行，也应存在如实反馈义务。

### 6.3 TREC 式长度效率

每种已校准语言/复杂度 profile 固定基础预算 `b0`、每信息点预算 `b` 和 optional 上限 `rho`。这些参数来自开发集，不由 Judge 逐个回答决定。

设正确覆盖的 optional 数为 O：

```text
C = min(O, rho * M)
B = b0 + b * (M + C)
E = min(1, B / L)                 # M > 0 且 L > 0
E = 0                            # M = 0 或没有送达任何回复
```

optional 只提供受限预算，不进必答召回率；没有 required 覆盖时 optional 不能独立撑起高分。重复命题只计一次。基础预算每个程序确定的请求窗口仅给一次，不按 Agent 发言数量发放。

optional cap 用于承认少量有帮助的补充，又避免任意多补充获得无限预算。候选开发值可从 `rho=0` 和 `rho=0.25` 比较，最终发布值须冻结。`b0`、`b` 不在方案阶段拍脑袋定成标准常数。

第一版明确存在信息点复杂度差异。通过开发集检查数值回答、名单、操作反馈、失败原因等类别；确需多 profile 时由用户请求/证据类型按固定规则选择，不能让 Judge 在看到回答后自由选择更宽松预算。无法可靠归类的样本效率 unavailable。

短于预算不继续加分，避免奖励极端压缩。L=0 而已确认应有反馈时 R、E 和综合分为 0；文本丢失则 unavailable，不当成沉默。纯“好的”即使很短，M=0，E=0。

### 6.4 候选综合分与真实性

先输出两个维度，不把信息密度直接称为正确性。另计算偏重完整性的候选分：

```text
F3 = 10 * E * R / (9 * E + R)     # E=R=0 时为 0
raw_feedback_score = 100 * F3
```

beta=3 是保留 TREC 偏重覆盖思想的候选，需人工评测比较 beta=1/2/3；正式发布前冻结，不能在观察正式模型排名后选择。

另输出 `fidelity_status = supported | material_error | uncertain`。有明确实质性错误时，候选正式分 `feedback_score=0`，同时保留 raw 分便于诊断；存在影响结论的真实性未知时不给确定正式分。该门控针对反馈中实质误导，不因为任务 reward=0 而触发。

这意味着“失败但诚实反馈”可以得高沟通分；“大量正确事实中夹带错误成功承诺”不能靠覆盖率和长度获得高正式分。可读性/可理解性没有在 v1 自动门控中充分解决，必须作为人工验收维度，不能把本指标当成完整语音体验分。

有 U 或 optional 未知时，保留分母和未知权重，用 M/O 的上下界计算 E、R、F3 区间。若真实性 uncertain，候选正式分下界为 0，上界为原覆盖/效率上界。不得把未知样本默认为 0 或完整证据后排除未知信息点。

### 6.5 数值样例

以下预算仅为算例，不是发布参数：G=4、b0=10、b=15、O=0。

| 情况 | M | L | B | R | E | 100×F3 |
|---|---:|---:|---:|---:|---:|---:|
| 完整精练 | 4 | 60 | 70 | 1 | 1 | 100 |
| 完整但长 | 4 | 140 | 70 | 1 | 0.5 | 90.91 |
| 很短但只答一点 | 1 | 20 | 25 | 0.25 | 1 | 27.03 |
| 无实质信息 | 0 | 10 | 10 | 0 | 0 | 0 |

F3 对完整但长的答案扣分较轻是有意偏重覆盖；若人工听评认为扣得不够，开发阶段应选择其他 beta，而非隐藏这个特性。长度效率 0.5 始终单独展示。

## 7. 音频辅助数据

基于实际 playback 提供：

- `agent_speech_seconds`：VAD 语音区间并集时长。
- `agent_playback_seconds`：实际播放音频的时长，明确是否包含句内停顿；不能用整通通话时长代替。
- `required_nuggets_per_speech_second = M / agent_speech_seconds`，M=0、已确认无语音或音频缺失分别按约定处理，不能将缺失除成高密度。
- 请求结束到第一次关键反馈的时间，仅在有可靠时钟与片段边界时计算；完整命题首次送达时间可作后续扩展。

没有词级对齐时，不按字符比例分配信息点时间；该时间指标为 unavailable。每秒事实数不作为 v1 主分或跨任务无条件比较，避免语速、名单复杂度、语言差异和可理解性混淆。

语音转写可验证、音频缺失时，文本分仍可用，音频指标缺失单独报告。只有生成文本而无法证明已播放时，不给用户侧反馈覆盖满分。

## 8. 状态与特殊情形

| 情形 | 处理 |
|---|---|
| 工具成功，Agent 说失败 | 根据结果/交付证据判错或时序未知，不照 Agent 的自述生成清单 |
| 工具超时、可能已生效 | 要求说明不确定，不要求确定失败 |
| 无权限 | 如实说明限制；不能要求用户提供密码或虚构可用授权流程 |
| 模型自己没尝试 | 完整证据下要求如实说明未完成；任务 reward 单独反映失败 |
| 用户要求重述 | 可以形成新的反馈义务，不简单判重复 |
| Agent 自己重复承诺/播报 | 增加 L，不增加信息点和基础预算 |
| 必须澄清对象/取得确认 | 能证明必要性时建立相关沟通要点；不因句子是问题而排除 |
| 最终答案正确但提前误报成功 | 保留错误，真实性门控或 unknown；不能仅看最后一句 |
| 查询值需要复杂计算、证据无法核实 | 信息点真值未知，不能用 Agent 答案当标准 |
| 请求取消、要求修改 | 按实际时间范围保留/撤销义务，不把旧目标全部算漏答 |
| 沉默 | 有完整交付证据时记 0；缺数据时 unavailable |
| API / Judge 失败 | grader_error，不算模型沟通失败 |
| 基础设施/用户模拟器出错 | 保留 diagnostic_only，不进入有效样本主汇总 |
| 正常超时/MAX_STEPS/模型业务失败 | 只要证据完整就评价，不因失败而删除 |
| 历史运行没有执行证据 | 首版默认 unavailable，不从旧聊天中猜成功；纯对话模式需单独 profile，后续再做 |

## 9. 缓存、预算与落盘

每个窗口通常两次 LLM 请求；若整个 trial 有三个有效窗口，通常六次，不宣传为“整通一次”。允许两阶段独立配置模型，默认可同模型、隔离请求历史。

- 第一阶段/第二阶段各设明确 request budget，使用现有 `RequestBudget`，所有修复/网络重试均计入实际尝试。
- 先实现无自动语义重试；结构无效默认失败，显式重跑重试失败阶段。若增加一次格式修复必须配置化、版本化、计费透明。
- 第一阶段成功缓存可在第二阶段失败后复用；不重新生成清单直到获得有利分数。
- 控制输入和输出长度、timeout、concurrency；不自动换模型。
- 工具结果/状态的投影必须确定性，保留关键业务字段、来源哈希和省略说明。被省略内容是未知，不是不存在。
- 不使用第三个 LLM 自动摘要证据。必要证据超限则 unavailable；后续分块版本需独立设计和人工验证。
- 调用价格使用实际 provider usage/cost，不在计划中承诺固定费用。

第一阶段 cache key：实际用户文本、窗口边界、规范化执行证据、可信历史、rubric/schema、原子化规则、模型 profile。

第二阶段 cache key：第一阶段冻结清单哈希、实际待测文本、必要证据、对齐 rubric、模型 profile。评分 key 另含长度规则和预算校准版本。

沿用 `artifacts/task_<id>/sim_<id>/diagnostics/evaluations/<profile>/`：

```text
conciseness.json
conciseness/
  input_manifest.json
  windows.json
  window_<id>/
    evidence_projection.json
    nuggets.json
    alignment.json
    validation.json
    scores.json
  requests/
```

每份结果记录来源哈希、model/rubric/calibration 版本、actual attempts、状态、错误原因和可复核的分子分母。原始模型响应由请求层保存，校验失败响应也需可追溯，不能只保存成功解析的 JSON。

现有 suite 的总体 profile 包含全部 measures 配置；新 measure 的阶段缓存应有自己的内容 key。不能因为同套其他 measure 的模型改变就悄悄重新抽一份标准。

## 11. 汇总与公平比较

- 窗口内计算 R/E/F3，预算不能跨请求转移；短回答的剩余预算不抵扣其他请求的长回复。
- trial 分数为其已送达、适用窗口的等权均值，所有窗口数和缺失数一并展示。存在不可评分的适用窗口时，完整 trial 主分为 null，保留可评分窗口诊断和区间，不只挑成功窗口。
- 对已送达而沉默的窗口记 0，未送达阶段报告 stage coverage；总体任务 reward 仍按现有连续任务规则处理。
- benchmark 主汇总对有效 trials 等权，若需要任务等权，则先每 task 平均 trials 再平均 tasks，并明确发布口径；首版推荐后者。
- 同时给 required 信息点的 micro coverage；不平均每秒事实密度、不用总 budget/总 length 替代窗口效率均值。
- 按语言、domain、结果状态、复杂度和证据模式分组，特别显示成功、失败和未知结果的数量。不能只展示成功任务的沟通分。
- 比较同一组 task/trial，并报告共同有效样本和各自全部样本覆盖，避免缺失 Judge 结果较多的模型占优。
- 不同 rubric、模型、预算校准、字符规则和候选 beta 分开报告，不混合成同一个排名。
- 报告预期 trial 数、送达窗口数、可评分率、unknown 比例、grader 错误、真实性错误率、原任务成功率。

## 13. 验证与校准

### 13.1 无 API 单元与集成验证

公式/边界：完整精简、完整超长、漏答、纯 optional、纯礼貌、无回复、N/A、unknown、零分母、optional cap、跨窗口无预算转移、F3 上下界。

证据/隔离：第一阶段没有当前 Agent 回复和隐藏要求；同一证据换回复不改变信息点 key；未来阶段不能进入输入；并行/未知时间不猜测；省略证据不当成否定。

语义契约 fixtures：成功、失败、部分成功、超时未知、权限拒绝、未尝试、澄清、撤销、用户要求复述、先错后改、提前成功声称、长名单、不同单位/否定/量词。

工程：schema 和引用全覆盖、错误缓存、失败保留、两阶段恢复、预算耗尽、dry-run 无模型调用、suite 其他指标回归、CLI/显示和原 reward 不变。

不为每条可逆文档编辑写测试；进入代码实现后针对真正评分语义写测试。执行适当的 `tests/test_diagnostics` 和受影响 runner/display 测试，提交前运行 `make check-all`；依赖调用使用 `UV_FROZEN=1`。

### 13.2 人工开发集

建议首批 40–60 个完整请求窗口，覆盖成功/部分完成/失败/未知/澄清以及短答案、名单和复杂过程。优先使用真实已保存轨迹；缺少类别可补小型受控 fixtures，但与真实模型能力样本分开。

两名标注员独立：

1. 不看待测回复，依据请求与执行证据列 required/optional 信息点。
2. 核对自动清单的遗漏、多余要求、粒度、错误真值和不可支持的原因。
3. 看/听回复，标记覆盖、误导、可删除表达、是否易理解，以及成对更偏好哪一条。
4. 分歧由复核者归因，不把所有分歧简单多数投票隐藏。

预算校准不使用待测模型原始长回复作为“合理长度”：为同一冻结清单准备人工认可的精练、完整、自然口语反馈，用其长度拟合保守预算。语言和任务复杂度需要代表性数据；未覆盖类别不宣称已校准。

### 13.3 受控变体

同一证据和信息点清单下，构造：

- 保持含义的自然精简、冗长改写。
- 同义重复一遍/多遍、插入无关背景或内部过程。
- 删除一条必答信息、替换数值/单位/对象、将不确定改为成功。
- 增加合理 optional，增加大量正确但无关的事实。
- 分成更多 Agent 发言、修改标点或空白。
- 改变 TTS 语速但保持文字，确认主文本分不变化。

期望：无信息新增的变长不提高效率；漏答降低覆盖；错误事实不能获信用；拆分发言不增加基础预算；同义表达稳定；过度压缩且难懂不能作为人工认可的预算参考。

### 13.4 开发与验收

开发集和留出验证集分开，预算、rubric、beta、optional cap 在开发集确定后冻结。正式模型结果不能反过来影响预算。

初步验收目标（属于开发目标，不是既有实测成绩）：

- 无证据来源或未来阶段引用的 matched 不得进入最终计数，结构审计通过率 100%。
- 人工复核的 required 信息点 precision/recall 目标均不低于 0.90；单列状态与语言表现。
- 清晰 matched/missing/contradicted 标签与人工一致率目标不低于 0.90，uncertain 单列。
- 对清晰的“同义完整且更精练”受控对，偏好方向一致率目标不低于 0.90。
- 多次独立抽取的点数/必要性漂移、人工精简偏好一致性、score 相关性和置信区间全部报告；语义不稳定的类别不得发布正式分。
- 真正的模型失败保留、基础设施失败不混入；未校准类别和证据缺失覆盖透明。

若信息点可靠但长度预算与听感不一致，先发布覆盖、真实性、长度和时长诊断，继续校准效率；不为按时上线强行把候选分标为最终指标。

## 14. 实施顺序与交付

1. **证据预检**：对真实运行输出窗口与缺失报告，人工确认范围、时钟和可用性；不调用模型。
2. **两阶段原型**：离线生成清单与对齐，保存所有中间结果；先输出计数和覆盖，无正式长度分。
3. **人工校准**：建立独立开发/验证集、检查原子化和状态规则，拟合并冻结预算。
4. **评分与集成**：实现确定性公式/未知区间、sidecar、CLI、summary、展示和失败恢复。
5. **留出验收**：核对受控变体与真实听评，记录局限，发布校准版本；再评估是否启用新运行 auto_score。

最先需要验证的不是某个 b 或 beta，而是：不看待测回复时，Judge 能否根据真实运行证据稳定地列出用户确实需要的反馈信息点。
