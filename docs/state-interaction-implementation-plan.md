# 对话状态交互评价：原设计落地实施计划

状态：已实施。新指标版本为 `tau-state-interaction/2`，状态轨迹版本为 `tau-dialogue-state/2`。本文将 [原状态交互计划](state-interaction-plan.md) 展开为具体实现步骤，并在末尾记录实现方式、运行配置与验证范围。

## 1. 本次目标与边界

建立通用的对话状态管理机制，正确保存事件顺序、可见信息、目标与待办变化，并据此计算两个主要指标：

- **Progressivity**：Agent 是否推进任务，或完成必要的交互工作。
- **Grounding**：Agent 的回复、问题、工具动作或承诺，是否正确使用当时可见的状态与证据。

本次优先完整落实原计划。暂不替换 `interaction` 的 LLM Judge，不重新定义 `effective_interaction_rate`，不新增整体完成指标，不处理另一个 Agent 正在审查的参考答案问题。

当前讨论中其他暂缓修改的指标决定，也不在本轮顺手实施。

状态机制位于评测侧，用已记录事件重建状态，不成为待测 Agent 的内部记忆或决策器。

## 2. 目标流程

```text
用户发言、Agent 行为、工具和后台事件
                 ↓
按真实发生顺序与参与者可见顺序整理
                 ↓
解释当前事件的含义，更新通用对话状态
                 ↓
保存行动前、工具调用前、回复前、窗口结束后的状态
                 ↓
Progressivity：相关业务或必要交互是否推进
Grounding：行为是否正确使用当时可见的状态
                 ↓
两个主要分数 + 状态轨迹与解释明细
```

不新增 Task alignment、Action fit、Claim fidelity、事实写入率、状态修改率等主指标。相关概念作为状态记录或 Grounding 原因码保存。

## 3. 当前实现与原设计的主要差距

| 原计划要求 | 当前情况 | 本次处理 |
| --- | --- | --- |
| 通用目标与待办，明确完成条件 | 不少初始化和完成判断依赖取消、退款、预订等关键词 | 改为通用待办和领域完成条件 |
| 候选事实与不确定性 | 有不确定记录，但主要通过覆盖当前值更新事实 | 保留候选、否定、过期、冲突及来源 |
| 分开记录 Agent 声明与权威事实 | 已有不同集合 | 保留并明确不可相互覆盖 |
| 完整消息顺序和调用 ID | 部分窗口通过不同时间基准的数值直接比较归属 | 按真实顺序、调用关联及交付时间组织 |
| 行为发生前的状态快照 | 主要只有窗口前后快照 | 补齐原计划的四类快照 |
| 未来结果不能支持先前声明 | Grounding 可能读取同窗口后来的结果 | 输入只提供行为前可见状态 |
| Agent 贡献与外部变化分开 | 用户新事实、成功调用可能直接触发进展 | 明确变化归属与目标关联 |
| 已满足事项不重复计进展 | 已有边界判断 | 保留并扩展到所有待办完成路径 |
| 首次问候只计一次 | 已有 establish_contact 初步实现 | 保留一次性必要交互项 |
| Grounding 按状态使用机会计算 | 仍有关键词、词语重合与窗口整体判断 | 改为具体行为对相关状态的使用记录 |
| 正常 Agent 陈述都进入分析 | assistant_context 与 agent 角色筛选不统一 | 归一化角色后再生成行为事件 |
| 与其他指标一起保存和汇总 | 单独计算的配置可能落入另一目录，被最新报告遗漏 | 整理为同一评测配置和报告归属 |

### 已用小样例确认的问题

- 参考回复为数字 `6`，实际回复 `9`，当前空词集合包含判断会误将信息交付标为完成。
- 用户补充收件人，Agent 提出无关问题，用户新事实仍可能让窗口被标为 forward。
- Agent 先声称邮件已发送，工具后来才成功，Grounding 可能以窗口末状态支持先前声明。
- 合理的初始确认尚未通过完整的交互待办机制表达，可能只得到 stagnated。

这些样例用于说明需修正的机制，不是把实现限制为只识别这几种句子。

## 4. 状态模型

在现有 `DialogueState`、`StateItem` 基础上调整，不另建通用工作流系统。

| 状态内容 | 含义 |
| --- | --- |
| 目标 | 用户当前希望达成什么，保留修改和取消关系 |
| 待办 | 未完成的业务工作或必要交互工作 |
| 事实及候选值 | 已明确值、歧义候选、否定、过期和冲突 |
| 约束 | 条件、禁止事项、授权、时间和对象范围 |
| 操作 | 请求、接受、执行、成功、失败、取消等实际进度 |
| Agent 声明 | Agent 声称发生了什么、承诺做什么 |
| 对话历史 | 实际交付的发言及对应事件 |
| 可见性 | 信息何时对用户、前端或后台可见 |
| 不确定信息 | 无法可靠确认的内容与原因 |

每个状态项关联稳定 ID、所属目标或事项、当前值和状态、来源事件、可见位置及更新时间。优先使用事件 ID 或状态版本引用，不重复拷贝整段历史。

### 4.1 三类信息分开保存

1. 用户要求与用户陈述的事实。
2. 工具或后台提供的执行事实。
3. Agent 的声明和承诺。

Agent 说“邮件已发送”只创建声明，不直接把对应操作改为成功。真实工具结果可以支持或否定声明，但声明不能覆盖工具结果。

### 4.2 候选和修改

同一事实存在多个合理候选时，保留候选及其依据，不提前强制选择。用户明确纠正后，旧值过期、新值生效，保留修改关系与原始来源。

保留原计划的主要状态生命周期：

```text
事实：unknown → mentioned → grounded → denied / stale / conflicted
待办：open → in_progress → satisfied / blocked / cancelled
操作：not_started → requested → accepted → running → succeeded / failed / cancelled
```

上述状态按实际证据更新，不要求每个任务机械经过所有节点。

### 4.3 初始信息与未来阶段

初始用户已知信息不等于 Agent 已知信息。尚未告知 Agent 的个人事实、隐藏信息，以及未来阶段要求，只保留为评测侧背景，不能成为 Agent 当前可见事实或已经生效的义务。

当用户请求实际交付时，才激活对应目标、约束和待办。已知信息通过真实发言或结果交付，才进入相应参与者的可见状态。

## 5. 事件顺序、时间与窗口

### 5.1 文本交互

保留完整消息顺序和工具调用 ID。调用请求与返回通过 ID 关联，不用“下一条看起来相关的回复”猜测归属。

不能把消息序号和运行秒数直接比较大小。文本事件顺序明确时使用原顺序；其他时间信息保留自己的来源。

### 5.2 语音交互

复用已实现的媒体时间记录，明确区分：

- 用户内容实际送入；
- Agent 回复实际交付；
- 工具操作发起；
- 工具执行完成；
- 工具结果对对应 Agent 组件可见；
- 后台结果或通知对前端可见。

工具执行完成不自动意味着前端已经收到结果。Grounding 使用被评价行为所在组件当时可见的证据。

现有日志不足以确定可见时刻时，保留未知，不用执行完成时间补造交付时间。

### 5.3 交互窗口

沿用原计划：以 Agent 回复为窗口结束点，组织此前相关的用户事件、工具请求、返回和回复。

窗口是记录容器，不赋予窗口内所有事件互相可见的权限。评价某个动作时仍使用其发生前的状态。

- 工具结果晚于某次回复时，进入后续状态，不能倒挂到前一次回复。
- 通话结束时未完成的事项保留为尾部状态，不伪造回复或完成事件。
- 对语音流中的跨时段回复，保留已知片段时间；只有整段粗时间、无法确定某项声明时刻时，不使用后到证据强行判定。
- 后台事件也需要有明确归属和可见位置，不能生成后因没有窗口 ID 就丢弃。
- 统一 Agent 角色表示，避免普通陈述因内部命名不同被漏掉。

## 6. 四类状态快照

| 快照 | 用途 |
| --- | --- |
| `state_before_agent` | 当前输入处理后、Agent 开始行动前的可用状态 |
| `state_before_tool_action` | 每次工具操作发起前的事实、前提与约束 |
| `state_before_agent_reply` | 回复前已可见的结果与待办 |
| `state_after_window` | 本轮结束时的状态和变化 |

一轮有多个工具操作，就分别保留对应的调用前状态引用。

实现使用状态版本或增量引用，必要时物化快照；不要求每个事件复制一份完整业务数据库。业务执行状态继续引用已有证据。

Grounding 的输入结构只暴露行为前可见状态。禁止未来证据影响先前判断，通过这一机制保证，不额外建设评分后审计模块。

## 7. 通用待办和完成条件

每个待办明确表达：

```text
要完成什么
针对哪个对象
所属目标
适用条件与约束
当前状态
可用于说明完成的证据
```

### 7.1 业务待办

包括查询答案、发送邮件、修改日程、取消任务等实际目标。一次工具调用成功，只说明该调用成功，不能自动满足所有相关事项。

### 7.2 必要交互待办

包括首次建立联系、补齐信息、澄清歧义、必要授权、回应进度询问、结果交付、说明障碍与后续安排。

提出问题前应存在相应未解决事项。必要提问可以推动事项进入处理中，获得明确答案后再完成澄清；不因为句子带问号就创建有效进展。

首次必要问候关联一次性 `establish_contact`。重复问候不能创建新的同类进展。其他确认与告知也必须对应当前实际需求，不能通过重复表达持续增加完成项。

### 7.3 领域适配职责

领域适配提供：

- 工具参数、返回值的含义；
- 对象身份和结果引用的关系；
- 操作的业务效果；
- 某类目标或待办的完成条件。

通用状态更新层负责状态迁移。移除在通用层中通过工具名字含 cancel、refund 等关键词就宣布完成的规则。

参考信息可以辅助描述目标，但不把参考调用次数、唯一工具路径或参考作者选择的执行顺序变成通用完成条件。参考数据审查由另一任务处理，本轮不重写数据集。

## 8. 自然语言解释与程序状态管理的分工

原计划没有要求所有语义均由正则表达式实现。为完整处理改口、否定、条件、澄清和结果交付，本次建议采用以下实现分工：

| 内容 | 处理方式 |
| --- | --- |
| 调用 ID、参数、返回、状态、顺序、时间 | 直接读取结构化证据 |
| 明确数值、对象、时间等比较 | 按类型进行确定性比较 |
| 用户目标、纠正与取消的含义 | 必要的语义提取 |
| Agent 回复、问题、承诺的含义 | 必要的语义提取 |
| 表达是否正确使用相关事实 | 必要时进行语义判断 |
| 状态迁移、去重、完成边界、计数和汇总 | 程序执行 |

复用现有 `state_interaction` 模型配置和调用工具，不增加新的模型服务或独立调度系统。

模型输入限定为当前事件、相关历史及对应可见状态，输出结构化含义、事项关联和证据来源。模型不直接输出整题总分，不直接覆盖工具事实。

语义无法确定时保留不确定，不通过额外裁判反复检查，也不新增多轮自动验收。

这是本次为实现原设计提出的具体实现方式，原设计没有固定要求必须使用哪种模型。由于它会改变当前状态模块主要靠规则运行的方式，实施时必须同步模型配置、调用预算和文档，不在原有调用链里隐式加入未说明的模型调用。

## 9. Progressivity 的实现

### 9.1 分开记录变化来源

窗口内变化先区分：

- 用户提供或修改的信息；
- 环境、后台自然变化；
- Agent 发起的动作及其结果；
- Agent 完成的必要交互。

用户或外部变化可以更新状态，但不自动作为 Agent 的进展。只有与 Agent 行为有对应关系、且与当前目标或必要交互相关的变化，才进入它的进展判断。

### 9.2 进展规则

- 用户主动补充联系人，只更新事实；Agent 正确利用它继续处理，才可能形成相应进展。
- 与任务无关的成功调用，不计业务推进。
- 用户合法取消目标，不自动计 Agent 倒退。
- 已满足事项重复出现，不重复计分。
- 满足事项只记录未满足到满足的状态边界。
- 相关操作的结果满足领域完成条件后，才完成对应业务待办。
- 外部等待、失败和阻塞关联到当前事项；条件解除后结束阻塞，不能一直影响后续窗口。

`goal_progress` 与 `interaction_progress` 可作为解释明细，分别表示业务推进与必要交互推进，不新增顶层指标。

### 9.3 窗口结果与分数

沿用四类结果：`forward`、`stagnated`、`regressed`、`externally_blocked`。

同一窗口同时存在明确倒退和推进时，建议沿用明确倒退优先的总体标记，并保留两类变化明细。只有相关外部阻塞、没有 Agent 可归属的推进或倒退时，单独标为 externally_blocked。

```text
forward_rate
    = forward 窗口数
      /（forward + stagnated + regressed 窗口数）
```

证据不足的窗口使用独立的可评分状态表示，不强行塞入 stagnated，也不为此扩展为整套评测有效性政策。

## 10. Grounding 的实现

### 10.1 按实际状态使用机会评价

对每个具体回复、问题、工具动作或承诺，先明确它实际用到了哪些状态。

| 行为 | 核对的状态 |
| --- | --- |
| 询问收件人 | 收件人是否已明确、是否出现新歧义或修改 |
| 发起邮件发送 | 当前收件人、内容、授权与必要前提 |
| 声称发送成功 | 对应操作是否已有当时可见的成功证据 |
| 承诺修改日程 | 目标对象和当前用户要求是否一致 |
| 询问附件 | 核对附件相关信息，不因未提及收件人而扣分 |

每条记录包含行为 ID、行为类型、相关状态项、行为前状态版本、证据来源、判断和原因。

### 10.2 标签及原因码

判断保留：

```text
consistent
inconsistent
unsupported
uncertain
not_applicable
```

以下只作为原因码：

```text
stale_state_use
ignored_constraint
unsupported_claim
contradicted_claim
irrelevant_action
invalid_precondition
wrong_entity
missing_required_state
```

移除用词语重合直接判定一致性的分支。没有使用某个状态的机会，就不为它生成扣分项。状态管理器知道某项事实，也不自动证明 Agent 使用了它。

### 10.3 计数单位与公式

从当前的窗口整体标签，改为原计划要求的实际状态使用机会。每项机会锚定具体行为及相关事项；同一行为对同一事项重复提及要去重，不按 JSON 字段数量扩大分母。

```text
consistent_rate
    = consistent 机会数
      /（consistent + inconsistent + unsupported 机会数）
```

uncertain、not_applicable 只留明细及适用计数。同一窗口既有正确也有错误行为时，都保留，不能被一个窗口标签覆盖。

## 11. 必须一并修正的当前问题

| 当前问题 | 机制修正 |
| --- | --- |
| 数字 6 与 9 因空词集合被误判匹配 | 数值按类型比较；语义表达依据明确含义，不使用空集合包含作为完成依据 |
| 用户新事实自动算 Agent 推进 | 状态变化有来源，只有 Agent 对应贡献计进展 |
| 无关调用成功自动算推进 | 调用关联具体待办与完成条件 |
| 后到结果支持先前声明 | 行为前可见快照限制 Grounding 输入 |
| 普通陈述角色不一致而漏评 | 统一事件角色表示 |
| 后台事件无窗口 ID 而被忽略 | 将其按发生及可见顺序更新对应事项 |
| 约束只保存、不实际参与判断 | 通过相关状态使用机会检查约束使用 |
| 分数难以解释 | 从保存的状态边界与机会记录直接派生分数 |

这些是原机制的实现，不新增评分之后的自我审计或验收阶段。

## 12. 运行、保存和汇总

### 12.1 单一配置与报告归属

`state_interaction` 与同次运行的其他指标使用明确一致的评测配置及报告归属。修复单独计算落到另一目录、随后最新报告看不到状态分数的问题。

自动执行必须使用有效的配置、模型和预算，不临时创建与本次运行不同的配置来隐式调用模型。保留现有模型调用缓存和资源限制即可，不增加第二套审核流程。

### 12.2 输出

- `state_trace.json`：事件、状态版本、窗口变化、状态使用机会及原因。
- `state_interaction.json`：两个指标和必要计数。
- 汇总能力面板：只展示以下两项。

```text
state_interaction
├── progressivity.forward_rate
└── grounding.consistent_rate
```

### 12.3 汇总与历史兼容

同题多次适用试验先平均，再对题目等权平均。缺少有效判断时保留空值，不填成 0 或 1；适用数量进入日志。

状态定义与 Grounding 分母改变后，更新版本标识。历史文件保留原解释；缺少真实顺序或可见性信息时，不伪造新证据，也不强制批量重跑历史记录。

## 13. 修改位置与实施顺序

| 顺序 | 主要位置 | 工作与产出 |
| --- | --- | --- |
| 1 | `diagnostics/state/models.py` | 补齐目标、待办、候选、可见性、状态版本和状态使用记录 |
| 2 | 既有证据收集入口、`diagnostics/state/events.py` | 保留真实顺序、调用 ID 和结果交付，统一角色及时间依据 |
| 3 | `diagnostics/state/projector.py` | 按事件更新，形成四类快照，区分用户、Agent 和外部变化 |
| 4 | 状态模块内小型领域适配入口 | 工具效果、对象关系和完成条件，替换通用层业务关键词特判 |
| 5 | 语义解释入口、`diagnostics/config.py` 与示例配置 | 提取请求和行为含义，复用现有模型调用、预算和缓存 |
| 6 | `diagnostics/state/metrics.py` | 从 Agent 相关变化计算 Progressivity，从状态使用机会计算 Grounding |
| 7 | `diagnostics/suite.py`、`runner/simulation.py` | 统一执行、保存、最新报告和汇总归属 |
| 8 | 指标清单、原设计说明及示例 | 更新真实实施状态、模型用途、计数口径和版本 |

先完成输入与状态机制，再实现分数；不沿用错误状态产出分数后再用一层层检查补救。

具体文件拆分以职责清晰和改动范围小为原则。领域规则可以单独放在状态模块的适配文件中，但不需要插件框架、额外服务或新数据库。

## 14. 轻量开发验证

使用人工构造的短对话、工具记录和已有离线样例，覆盖以下机制即可：

1. 用户改口后旧值过期；未告知信息不成为 Agent 可见事实。
2. 多个调用通过 ID 对应，后到结果不能支持先前声明；文本序号不与秒数混用。
3. 数字 6 与 9 不匹配，正确的明确数字可以满足对应交付事项。
4. 同一完成事项不重复计进展，首次必要问候只计一次。
5. 无关成功调用不算推进，用户补充事实不直接算 Agent 进展。
6. 正确使用当前事实、使用过期对象、无依据声明，产生不同 Grounding 结果。
7. 外部等待与 Agent 停滞分开，解除阻塞后正常继续。
8. 完成运行后，两个指标与其他指标一起出现在同一报告入口。

测试中的语义调用使用固定返回替身。只有出现语义规则无法判断的具体问题时，再考虑少量已有对话的真实模型试读，不预设全数据集或大规模真实 API 验收。

不新增运行前验收、逐窗口复核、双裁判交叉检查或自动反复重评分。结构化数据仍使用既有的数据模型解析；正确性主要由来源分离、可见状态、待办完成条件和计数单位保证。

## 16. 实施记录与使用方式

### 16.1 已落地的机制

- `models.py`：通用目标和待办、候选事实、约束、操作与声明分别保存；来源、可见角色、状态版本及历史明确记录。
- `events.py`：文本从完整消息顺序及调用 ID 重建，语音从本地单调时钟的实际请求／完成／结果发送记录重建。没有可靠映射的独立后台时钟不参与强行排序。
- `projector.py`：逐事件处理；行动前、工具调用前、回复前和窗口结束状态通过版本引用保存。未来事件不会进入当前语义输入。
- `adapter.py`：按实际工具返回或对应操作的业务状态快照判断完成，支持数值、对象、结构和结果路径，不以工具名字关键词宣布事项完成。参考轨迹不作为唯一允许路径。
- `semantic.py` 与 `semantic_prompt.md`：按当前事件与可见前缀解释请求、修改、候选、行为和状态使用机会。模型不直接计算总分，也不覆盖权威工具事实。
- Progressivity 只从相关 Agent 贡献产生；用户新事实、后台自然变化不直接计进展。同一事项完成不重复计分，外部阻塞可解除。
- Grounding 按行为与相关事项的机会计数，使用过期事实、未来证据、错数字、无依据声明分别记录；不再用词语重合直接判一致。
- 后台组件收到结果不会自动让前端知道结果；待办状态变化也按可见角色投影，防止经由“已满足”状态泄露尚未通知前端的结果。
- 诊断目录中的 `state_trace.json` 保存规范化事件、状态版本、窗口变化和机会；`state_interaction.json` 保存两个主指标。它们和其他已配置指标共用评分目录、summary 与 latest.json。

### 16.2 显式配置与模型预算

自然语言语义解释需要模型。因此移除旧的“保存运行就另外使用独立默认配置计算状态指标”路径。必须明确把 `state_interaction` 加到本次 `metrics_config.measures`，并启用 `auto_score`，才会自动评分；只采集证据不会隐式调用模型。

- `examples/state-interaction.yaml`：单独计算状态指标，使用配置中明确的模型，最多 96 次共享请求预算。
- `examples/real-metrics.deepseek-all.yaml`：已加入 state_interaction，使用同次运行的 DeepSeek 配置及共享预算，不再写到另一份评分目录。
- 一次用户发言、Agent 回复或工具发起需要一次语义解释；结果交付和确定性完成判断不另调用模型。复用现有缓存，无额外裁判复核或状态专用超时重试。
- 预算不足、输入不完整、模型无法解释或必要效果证据缺失时，相关窗口标记为不可明确评分，报告状态为 partial，保留可判断的样本和原因，不伪造成零分。需要的预算随实际事件数量而变，96 不是对每次对话够用的承诺。

可使用现有 CLI 对已收集证据执行：

```bash
tau2 metrics run <results-path> --config examples/state-interaction.yaml --only state_interaction
```

状态指标依然是独立诊断，不进入整题 reward，不替换 interaction LLM Judge。

### 16.3 历史数据与证据边界

旧证据没有完整调用交付位置时，只使用确定的对话顺序，不把旧运行秒数与消息索引混排，也不把未知结果交付当作已经可见。旧版本分数和新版本分数在汇总中分开。

初始私有任务描述、用户已知信息、参考回复与未释放阶段不会预先注入 Agent 可见状态。已经实际送达的用户目标作为系统当前业务要求；具体事实、工具结果及完成状态仍按照组件的实际可见性处理。

### 16.4 验证范围

126 项相关本地测试通过，包含 21 个状态机制测试及既有证据收集、任务汇总、公共音频和千问适配器测试。测试使用固定语义返回和人工事件，未调用真实模型 API、未运行整套数据集。

Ruff 和差异空白检查在本次修改文件上执行。额外运行原 interaction 测试时，仍遇到此前已存在的旧汇总／CLI 输出断言不匹配；没有为此恢复旧输出或修改其评分定义。

本次没有新增运行前验收、逐窗口双模型检查、评分后审计、自动重跑或专用验收脚本。真实模型解释质量及复杂场景覆盖仍取决于所配置模型与可用证据，不以本地机制测试宣称全数据集准确性。
