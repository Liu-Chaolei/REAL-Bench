# Gaia2 参考答案轻量修复计划

状态：计划已确定，尚未开始正式修复。

本计划用于修复 Gaia2 现有 1200 道题的参考答案、参考操作以及必要的评分内容。它采用已有 DeepSeek 审查结果作为逐题修复入口，不再额外建立一套重复的期望结果分析体系。

本计划与旧的详细 repair ledger 方案并行保留，但正式修复以本计划为准。旧方案中的逐条 ledger、问题分类表和期望结果表不作为本轮必需产物。

## 1. 基本原则

- 当前正式题库保持不变。
- 在独立目录中生成新的修复版本。
- 原始题库、快照和 DeepSeek 审查结果只读保留。
- DeepSeek finding 是修复依据和审查线索，不直接等同于必须修改的内容。
- 直接查看每道题本身、当前参考答案和 finding，判断该 finding 是否成立。
- 不预先规定问题分类，也不为每道题另建完整的期望结果表。
- 不建立逐条 repair ledger；修复版本本身以及版本 diff 作为修改记录。

## 2. 修复范围

修复对象包括：

- 参考事件及其工具参数；
- 参考事件之间的依赖和必要顺序；
- 参考回复和用户可见结果；
- 参考答案中的事实、对象、数量和筛选结果；
- 明确由题目问题导致的评分字段或检查条件。

用户请求本身只有在能够确认题目文本确实错误时才修改。不能仅因为参考答案与 DeepSeek 的建议不同，就改写用户请求。

## 3. 逐题修复流程

对每道题直接执行以下流程：

1. 读取原题、当前参考答案和该题的 DeepSeek 审查结果。
2. 根据 finding 指向的位置查看相关事件、阶段、快照或工具结果。
3. 判断 finding 是否成立：
   - finding 有充分证据：修改对应内容；
   - finding 与题目或快照不符：保留原内容；
   - 证据不足或存在歧义：暂不修改。
4. 同一道题的多个 finding 一起处理，避免单独修复某一处后破坏同题其他要求。
5. 修改后立即检查该题的数据结构、引用关系和参考执行是否仍然成立。

不把 DeepSeek 的 finding 数量直接当作修改数量。每次修改都以题目实际内容和现有证据为准。

## 4. 处理顺序

先处理 800 道 base 题，再处理依赖 base 题的变体：

- repetition：确认重复表达没有改变原题目标；
- mind_change：确认最终修改后的值与参考操作一致；
- AddTask：确认新增目标和新增参考操作正确；
- Modify：确认修改对象、绑定关系和变体评分语义正确；
- Cancel：确认取消对象、取消时机和原任务保留关系正确。

变体不直接脱离来源关系单独修复。base 题修复后，关联变体需要重新检查，必要时重新生成其运行视图。

## 5. 修复版本

修复结果写入新的版本目录，不覆盖当前正式数据。新版本至少保留：

- 修复后的 `tasks.json`；
- 修复后的变体数据或运行视图；
- 与数据对应的 manifest、来源 hash 和版本信息；
- 原始版本与修复版本之间的可查看 diff。

不另建逐条 finding ledger、期望结果表或预设问题分类统计。版本 diff 是本轮修改的主要记录。

## 6. 必要验证

修复过程中对修改过的题做轻量验证：

- JSON 和任务模型可以加载；
- 事件 ID、依赖目标和阶段引用有效；
- 依赖关系没有形成循环；
- 参考操作可以完成必要的 reference replay；
- 变体仍然能够正确绑定来源题。

全部题目修复后，对新版本执行一次完整 Gaia2 数据验证。验证失败时只回退有问题的修复版本，不修改原始题库。

## 7. 暂不做的事情

- 不重跑一轮与 DeepSeek 审查相同的全量问题分类；
- 不为每道题建立独立的期望结果规格；
- 不要求每条 finding 都产生一条状态记录；
- 不因为模型提出疑点就自动修改题目；
- 不在本轮重新设计整体 reward 定义；
- 不覆盖当前正式题库或原始审查归档。

## 8. 开始条件

正式修复开始前，确认以下内容：

1. 使用本轻量计划替代旧的重型 repair ledger 流程；
2. 当前正式题库保持只读；
3. 修复结果写入新的独立版本目录；
4. DeepSeek 审查结果作为逐题入口，直接结合原题和证据判断；
5. 只在修复版本完成验证后，再决定是否发布或替换正式版本。
