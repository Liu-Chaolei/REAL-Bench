# Modify、Cancel、AddTask 任务变体与指标迁移计划

状态：机制接线与 200 道 DeepSeek 生成草稿已完成，本地验证通过，具体记录见第 16 节。承接触发与绑定的详细实施方案见 [承接触发实施计划](modify-cancel-addtask-acceptance-trigger-plan.md)。未运行真实 Agent 的整批评测。

## 1. 目标与实施原则

在原 800 道主任务基础上构造三类变体：

| 集合 | 目标数量 | 核心交互 |
| --- | ---: | --- |
| AddTask（运行中追加任务） | 100 | 原任务进入后台后，新增一项要求，原任务继续有效 |
| Modify | 50 | 先提出临时要求，后台接收后，再修改这项任务的要求 |
| Cancel | 50 | 先提出临时要求，后台接收后，再取消指定工作 |

原 800 道题保留为来源，不覆盖原记录。新变体使用独立 ID。

核心原则：

1. 尽量复用现有数据构造、用户模拟器、后台观察、请求发送和指标计算代码。
2. Modify、Cancel 保留原参考答案作为来源资料，暂不以原参考调用路径或原 ENV 判断本变体表现。
3. 现有指标能直接用的直接用；需求理解与精简反馈主要调整输入组织、时间范围和请求归属，尽量保留公式及裁判规则。
4. 不删除临时请求或实际操作，不把真实执行记录改写成一条虚构的标准轨迹。
5. 运行正确性主要由请求 ID、任务 ID、事件时间和明确的交互流程保证。
6. 不在评测系统、评测流程或指标计算里新增重型验收、反复校验、自我审查、双版本对照、自动修复或失败重跑。

## 2. 本轮已确定与尚未确定的内容

### 2.1 已确定

- AddTask 100 道、Modify 50 道、Cancel 50 道，均从原 800 道主任务抽取构造。
- 这 200 道题的离线构造使用 DeepSeek，复用原有配置和凭据位置；具体配置见第 5.1 节。
- AddTask 插入新增要求，补充相应参考答案。
- Modify、Cancel 尽量通过改写请求和新增交互构造，保留原参考答案，不要求沿用原参考路径评分。
- 修改／取消前已经执行了一部分，或者尚未执行，均可能是合理情况；不能预先要求所有 Agent 都处在同一进度。
- 发言有用性复用原规则。
- `native_result_reward` 按现有含义复用，不要求它代表全局业务完成。
- `reply_reward` 复用现有规则及前置条件，不在迁移时顺带改变定义。
- Precision／Recall／F1、精简反馈四项需要仔细处理要求变化，但以机制和输入适配为主，不增加审核流程。
- Modify、Cancel 暂缓使用 Progressivity、Grounding、原参考路径四项执行分和原 ENV。
- 原题参考答案的全面审查已交给另一个 Agent，本任务不重复开展。

### 2.2 首版实施语义（已确认）

- Cancel 取消临时任务 B，原任务 A 继续；只停止剩余工作，保留取消前合法完成部分。
- A、B 合并处理或没有独立 B 时记为目标未绑定，不把取消 A 算作成功。
- Modify 继续只按原生 modify 操作的接受结果判断，不扩展到取消后重建。
- AddTask 要求承接新旧工作，不强制创建第二个独立后台任务，也不固定并行或整体顺序。
- 优先最后阶段，每题一次变化，不叠加通用 Query／Result。
- 200 道变体使用 200 个不同的 base 来源，不要求与 Mind Change／Repetition 来源完全不重合。
- AddTask 补齐新增参考后，允许启用补齐后的 ENV、现有执行质量与状态交互指标；是否计算仍由运行的指标配置选择。

这些语义已在实施前由用户确认。运行时按实际绑定、交付与操作记录执行，不新增语义审核裁判。

## 3. 三类交互的具体含义

### 3.1 Modify

示例：原题最终要求 15:00 的会议。

```text
第一次请求：安排在 14:00。
后台接收任务 T。
第二次请求：改成 15:00，其他不变。
Agent 对 T 处理修改，并继续任务。
```

第一条请求在改口前是有效要求。不能把它自动标为 Agent 理解错误，也不能删除对应操作。

需要明确保存：

- 修改的是同一项什么工作。
- 哪个参数、对象或条件发生变化。
- 哪些要求继续有效。
- 用户修正发生时，任务的实际状态。

第一版建议只改变一个清楚的业务要素，如时间、数量、地点、名称或已有对象选择。临时值必须有场景依据，不提前泄露原题需要查询的答案。

不要求必须在相关写操作发生前发出修改。先创建旧会议再调整、尚未创建就直接采用新时间，都保留真实记录；本轮不按固定参考操作列表处罚合法差异。

### 3.2 Cancel

建议的主要构造：

```text
原题任务 A 仍需完成。
用户临时增加要求 B。
后台接收 B。
用户取消 B，并说明 A 继续。
Agent 处理取消，保留应该继续的工作。
```

取消对象必须可以明确指认。首版取消表示停止剩余工作；撤销已完成结果需要用户明确提出，本批题目不要求撤销。

后台取消不等于自动撤回已经发送的邮件、消息等结果。保留操作实际开始、完成和取消确认时间，避免把在途操作的晚返回直接当作取消后的新执行。

Agent 没有单独提交 B 时，评测器不能替它拆任务，也不能把取消 A 认作成功取消 B。

### 3.3 AddTask

```text
原任务 A 已进入后台。
用户追加任务 B。
A、B 的要求同时有效。
```

第一版建议选择相对独立的 B：不撤销 A、不依赖 A 尚未产生的结果、不与 A 同时修改同一个对象。

补充 B 的参考操作、结果和必要依赖。用户没有要求优先级时，不固定 A、B 的整体执行顺序，也不自动要求底层并行。

## 4. 数据组织与来源管理

采用“原题＋变体差异记录”，加载时构造运行任务。不要建立第二套需要手工同步的完整原题库。

每条变体只保存必要信息：

| 信息 | 用途 |
| --- | --- |
| 变体 ID、类型、来源题 ID、来源版本 | 明确身份与可复现来源 |
| 目标阶段 | 指定插入位置 |
| 初始请求文本 | 原要求、临时替代要求或临时附加要求 |
| 后续请求文本 | 修改、取消或新增内容 |
| 请求关系 | 更新哪次请求、撤销哪项工作、是否新增独立任务 |
| 任务角色 | 管理目标及应保留的任务 |
| 触发方式 | 后台接收后，在适用状态发送 |
| 评分配置 | 本变体启用哪些指标 |
| 参考差异 | AddTask 的必要新增内容；Modify／Cancel 的来源参考可保持不变 |

字段名称优先复用现有结构。后台真实任务 ID 在运行时关联，不写进用户文本或预设答案。

Modify、Cancel 的原参考答案明确作为来源资料保留，不能因为字段还在，就被旧默认评分入口自动使用。

任务生成基于明确版本的原题。另一位 Agent 修正原题后，只核对受影响的变体，不自动覆盖对方工作，也不重做全量原题审查。

## 5. 题目构造与请求生成

复用现有变体构造器的数据读取、模型调用和来源记录能力，扩展为多轮交互，而不是只改写同一句发言。

- Modify：固定临时要求与后续修正。
- Cancel：固定临时工作及取消对象。
- AddTask：固定新增业务内容及其参考结果。

运行时可以直接使用保存的话术，也可以复用现有生成器改写表达。但生成器只负责自然表达，不临时决定修改什么、取消谁或增加什么业务要求。

建议每题只插入一次变化；优先选择后续阶段，具体位置由变体数据固定。

同源变体在未来训练／测试划分时应保持同侧，避免内容泄漏。这是数据组织事项，不增加评测运行步骤。

### 5.1 离线构造模型与凭据（已确定）

AddTask 100 道、Modify 50 道、Cancel 50 道的离线构造均使用 DeepSeek。
复用现有 `docs/gaia2-series.deepseek.config.json` 的 `author` 配置，模型、
API Key 和 API 地址继续通过以下环境变量引用解析：

- `DEEPSEEK_MODEL`
- `DEEPSEEK_API_KEY`
- `DEEPSEEK_BASE_URL`

原有私有配置文件位置为
`/hpc_stor03/sjtu_home/chaolei.liu/.config/qwaudio/config.env`，由现有
`config_env_file` 配置读取。无需移动或复制凭据，也不在计划、生成数据或来源记录中保存密钥值。
实际模型名称沿用 `DEEPSEEK_MODEL` 的配置值，不另行硬编码或切换提供方。

DeepSeek 负责离线构造固定的业务变更及必要参考内容；运行时仍按第 5 节的边界
交付已确定的要求。复用模型配置不改变第 2.2 节中已确认的题目语义和评分范围，
也不自动继承旧构造器的独立复审、失败重生成或全量参考执行流程。

## 6. 复用现有动态后台运行机制

已有能力包括后台事件观察、状态选择、用户请求发送、操作记录和回复收集。新增一个有明确题目内容的变体模式，复用这些接口。

```text
初始请求实际发送
→ 对应后台任务已接收
→ 后续请求进入发送队列
→ 后续请求实际交付
→ 收集管理操作、结果和回复
```

实现要点：

- 根据真实事件推进，不靠固定睡眠猜任务进度。
- 记录排队、开始发送和发送完成，评分不拿排队时间替代实际交付。
- 每个变体默认一次后续管理请求。
- 不暂停 Agent，不阻断其业务工具，不自动回滚环境。
- 不因失败再抽一个目标、重新生成请求或重跑。
- 没形成预期管理机会时保留实际状态，不自动转成 Query 后仍算管理变体成功。

请求交付后 Agent 未处理，与请求到达前任务已经结束，必须依靠时间记录区分；不能把所有失败都归为“错过时机”。具体成功／不适用分类沿最终确定的任务语义执行。

## 7. 共用请求关系与后台事件记录

尽量扩展现有证据结构，所有指标读取同一份事实。

```text
用户请求：
请求 ID、实际文本、交付时间、所属阶段、
新增／修改／取消类型、关联的前一请求

后台事件：
任务 ID、提交／更新／取消类型、实际参数或文本、
开始及完成时间、返回结果、调用或交付关联 ID

Agent 回复：
发言 ID、实际文本、开始及结束时间
```

题目关系只说明用户提出了什么，不能替 Agent 补出尚未发生的后台操作。后台预测输入只使用实际提交、更新、取消证据。

优先通过请求来源、任务 ID、调用 ID 和已有父子关系关联。不能可靠关联时保留未知，不增加一个专门匹配裁判反复猜测。

同一次更新的请求、返回和交付确认通过已有 ID 关联，避免计成多次独立执行。

## 8. 可直接复用的指标

| 指标 | 本次处理 |
| --- | --- |
| 12 项语音交互指标 | 修改／取消／追加作为正式发言，复用统一声音与时间线 |
| 发言有用性 | 保留现有裁判规则，加入真实请求变化及管理结果证据 |
| `native_result_reward` | 按现有 Modify／Cancel 条件评分，绑定本次目标任务 |
| `reply_reward` | 保留当前规则及前置条件，评价实际管理结果的回复 |
| 通话 selectivity 标记 | 从已有三项细分事件派生 |

### 8.1 发言有用性

现有规则已要求按发言当时的信息评价，并承认修改和取消自用户提出时生效。无需新增 Modify／Cancel 专用裁判标准。

输入组装加入已有后台管理记录。此前合理的确认或进度报告，不能因为用户后来改变要求而追溯变为无用。

### 8.2 `native_result_reward`

本次不扩大指标含义：

- Modify：绑定任务上出现相应修改操作，返回满足现有 `accepted=True` 条件。
- Cancel：绑定任务上出现相应取消操作，返回满足现有 `effect="cancelled"` 条件。

复用现有候选筛选与返回形式。该分数只表示当前定义下的后台管理结果，不改称整体业务成功。

主要接入变化是正确绑定目标：取消临时 B 时不能仍默认使用第一个后台任务 A。

### 8.3 `reply_reward`

保留当前行为：只有 native 结果通过且存在回复时，才按语义规则评分；其他情况沿现有行为处理。

不在迁移时顺带把它改为独立于操作成功的“失败解释准确率”。如以后要改变这个前提，另行讨论。

## 9. Precision／Recall／F1 的最小调整

### 9.1 保留已有流程与公式

继续使用已有需求提取、双向语义比较、重复处理、事实计数与题目等权汇总。

```text
Precision = 预测侧匹配事实数 / 预测侧有效事实数
Recall = 用户侧匹配事实数 / 用户侧有效事实数
F1 = 2PR / (P + R)
```

不增加新的语义复审模型，不因每次改口重跑一套完整评估。

### 9.2 预测侧接入真实管理事件

当前主要接收后台 prompt、steer 文本。扩展输入组织，使实际更新与取消事件也能表达：

```text
提交任务 T：创建 14:00 的会议。
更新任务 T：改为 15:00。
```

或：

```text
提交任务 B：整理额外清单。
取消任务 B。
```

保留实际参数、结果和对象关系；不能用用户预期内容补写缺失的后台更新。发出请求、接受请求、实际交付等是不同事实，按现有证据表达，不强行归并为成功。

### 9.3 保留要求的有效阶段

整通对话仍一次组织输入，但提取结果需要表达：

- 原要求在被修改／撤销之前有效。
- 更新替换同一任务中的哪部分要求。
- 未修改部分继续有效。
- 取消撤销的是哪项后续执行要求。

优先复用现有意图结构中的目标、关系、时间与限制。只有确实无法表达时才增加最小字段，不重建完整 schema。

GT 与预测独立提取。预测侧不能读取 GT 来自动修正错误。

### 9.4 现有裁判需要明确区分的含义

| 实际情况 | 应表达的判断含义 |
| --- | --- |
| 正确提交 14:00，随后正确更新到 15:00 | 前后都符合当时要求 |
| 只提交 14:00，漏掉更新 | 后续修改未正确传达 |
| 更新成 16:00 | 修改内容错误 |
| 用户取消 B，实际取消 A | 取消对象错误 |
| 同一任务的更新及交付确认 | 不自动变成重复执行目标 |
| 后台拒绝了内容正确的更新 | 传达内容与管理执行结果分别记录，不混成同一种错误 |

时间用于解释先后关系和有效范围，不新增隐含的固定传达时限。

## 10. 精简反馈四项的最小调整

保留 `required_coverage`、`length_efficiency`、`raw_feedback_score`、`feedback_score` 的现有公式、语义判断和语言长度预算。

### 10.1 让修改／取消形成明确反馈边界

当前主要按原题阶段划分反馈窗口。新增的修改／取消可能在阶段中间发生，因此使用实际交付的变更请求 ID 补充窗口边界。

不另请模型判断切段位置，不按每个音频包切段，不把普通确认或澄清都当成新业务请求。

### 10.2 携带必要历史，不重复要求旧信息

“改成 15:00，其他不变”需要前文对象、参与人等信息作为上下文。

上下文不等于新的反馈义务：不能要求 Agent 每次重复所有旧条件。取消后也不能继续要求交付已经撤销的完整成果。

### 10.3 管理证据进入原有信息点生成流程

把真实更新接受／交付结果、取消确认和实际任务状态，与已有业务操作证据一起提供给现有信息点提取器。

继续由原规则判断用户需要知道的内容，不固定要求每次取消都汇报一大段：

- 仅接受修改时，不当成业务已完成。
- 确认取消时，可以要求说明取消事实。
- 有必要的已完成部分或限制时，根据证据判断是否需要说明。
- 缺少证据不补造成功或失败。

### 10.4 保留时序，避免追溯误判

修改前正确说“14:00 已创建”，不因后来改成 15:00 被认作事实错误。

但修改前就已经虚构成功的回复，也不能因后面完成任务而被抹掉。旧窗口保持当时上下文，后续窗口使用最新有效要求。

### 10.5 回复和长度只统计一次

一段实际回复只归属一次。确认、进度及结果按业务请求窗口组织，不因为多说几句“好的”就新增多个长度预算。

回复跨越变更交付时点时，使用已有发言／转写时间信息；无法可靠拆分的部分沿用不确定表达，不让模型补造时间边界。

已有长度预算继续使用。没有校准配置的语言保留现有不可用情况，本次不新做预算校准。

## 11. 暂缓评分通过统一入口控制

Modify、Cancel 暂缓：

- tools、parameters、order、原参考路径 effects；
- 原 ENV Assertion；
- Progressivity、Grounding。

任务变体的评分配置声明适用指标，由统一入口选择。不要先执行评分再删除结果，也不要用 0 或 1 代替未启用指标。

原题正常运行的评分行为保持原有定义。历史结果也不重新解释。

`avg_reward`、`pass^k` 不自动继续统计这两类变体的旧 ENV。新的整体完成指标后续单独设计。

现有 `persistent_task.reward` 仍是已有 native 与 reply 的组合，不冒充整题完成分。

AddTask 按第 2.2 节已确认的范围，允许使用补齐后的 ENV、执行质量和状态交互；不与 Modify／Cancel 共用停用配置。

当前工作区的输出整理将已有后台组合结果显示为 `completion_score`，native 与 reply
判断保存在 `evaluation_log.native_result`、`evaluation_log.reply`。本文中的
`native_result_reward`／`reply_reward` 指这两项原有判断的含义与前置条件；迁移不改变其规则。
Modify／Cancel 的整题 `reward` 为 `null`，因此不会作为 0／1 纳入旧奖励汇总。

## 14. 轻量开发验证

只覆盖容易出错的行为，优先使用人工事件和已有离线样例：

1. 原请求正确提交、后续正确修改，旧要求不被误判为额外错误。
2. 用户已提出修改但后台没有更新，输入组装不能自动补成成功。
3. 取消 B 的事件不能关联成取消 A。
4. 后台实际结果与回复证据对应，不靠参考答案代替真实结果。
5. 修改前正确回复不因后来要求变化被追溯判错。
6. 取消后不继续要求交付已撤销成果。
7. 同一回复不重复计长度，同一更新事件不重复计意图。
8. Modify／Cancel 暂缓的指标没有被调用。
9. 原题和 AddTask 的评分选择不被 Modify／Cancel 配置误影响。

这些是开发测试，不进入评测主流程或指标计算。

不新增运行前全题审查、每轮自检、额外审核 Agent、反复语义验收、双重评分、失败自动重生成或全量 Agent 重跑。

新增题目的内容审阅属于离线数据制作。原题全面审查继续由已经负责的 Agent 处理，本任务只关心新增内容及其与来源题的关系。

## 15. 指标含义与本次边界

- `native_result_reward` 仍是现有后台管理结果分。
- `reply_reward` 保留当前前置条件。
- Precision／Recall／F1 评价需求传达，不代替业务完成。
- 精简反馈评价实际反馈的覆盖、长度及事实准确性。
- 语音指标评价实际交互时间和行为。
- 上述指标不自动构成新的整体完成指标，本轮不设计新的整题总分公式。

保留参考数据、正确采集事件、准确选择适用指标，是本次实现的机制基础。尚未明确的题目语义先确定，不用附加验收流程掩盖定义缺口。

### 16.2 已接通的机制

- 变体差异包含来源完整哈希、初始／临时／后续请求、关联短语、任务角色和新增参考。
