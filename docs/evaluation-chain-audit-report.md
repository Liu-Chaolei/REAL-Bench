# 评测整体链路审查报告

状态：分析完成，待逐项讨论。本文只记录当前代码结构和需要后续决定的问题，没有修改评测链路。

## 1. 本次审查范围

当前系统不是单一来源。主要由以下部分拼接而成：

1. τ-bench 的运行器、编排器、用户模拟器、Agent 接口和结果保存。
2. Gaia2 的题目、应用状态、场景事件和业务状态检查。
3. ARE／REAL-Bench 相关的应用工具、参数检查、操作匹配和执行明细评分。
4. 本地增加的三阶段连续任务、Dynamic Follow Up、交互变体和后台任务指标。
5. 独立的诊断体系，包括 intent、execution、voice、interaction、state_interaction 和 conciseness。

本报告关注会改变测试条件、评分事实来源或最终结果的链路问题。文件目录、一般重复函数、展示文字等细节暂不处理。

## 2. 当前总体链路

```text
任务数据、初始快照、参考事件
              ↓
      Runner 构造一次实验
              ↓
  Gaia2 Environment + ScenarioRuntime
              ↓
 User Simulator ── FullDuplex/Orchestrator ── 待测 Agent
       │                    │                    │
       │                    ├─ 工具调用 ── Gaia2 应用工具
       │                    ├─ 用户/Agent 交付事件
       │                    └─ 阶段和后台状态推进
       │
       └─ 语音、阶段请求、动态请求、音频播放
              ↓
   SimulationRun、environment_trace、ticks/messages
              ↓
  ENV / execution / intent / voice / state / feedback 评分
              ↓
       task-equal 汇总、展示、导出
```

真正需要分开的，是“运行时使用什么推动环境”和“评分时用什么判断 Agent”。当前两者在部分 Gaia2 场景事件上共用参考事件图，因此存在耦合。

## 3. 四类会改变交互流程的机制

### 3.1 Gaia2 原始参考事件与环境事件

题目中的 `scenario.events` 包含几类事件：

- 用户请求事件；
- 参考 Agent 操作事件；
- 环境自动事件；
- 参考 Agent 对用户的回复事件。

`ScenarioRuntime` 会保存事件依赖和完成状态。实际工具操作成功后，运行时尝试把它绑定到参考事件；参考事件被绑定后，依赖它的后续用户或环境事件才会释放。

对于参考 Agent 回复，运行时会把已经交付的 Agent 文本与参考回复比较。简单文本可以直接匹配，必要时使用语义匹配器。匹配成功后，后续依赖事件才会继续。

这条链路的用途原本是把场景中“操作完成之后才出现的环境变化”接起来，例如第三方回复、通知邮件、下一阶段前置事件。

它同时带来一个评测影响：**Agent 的合理表达如果没有被运行时匹配器接受，后续环境事件可能不释放。**因此参考回复匹配不只影响评分，也可能影响被测 Agent 后续看到的环境。

关键入口：

- `src/tau2/environment/scenario.py`
- `src/tau2/domains/gaia2/environment.py`
- `src/tau2/domains/gaia2/replies.py`

### 3.2 三阶段 ScenarioStages

三阶段机制是本地在 Gaia2 上增加的连续运行逻辑。`ScenarioStages`：

- 从 `scenario.stages` 找出每阶段的主要用户请求；
- 使用普通用户 STOP 信号作为阶段切换；
- 只有当前请求完整交付、Agent 输出和工具状态排空后，才释放下一个阶段；
- 保存每阶段 queued、started、completed、interruption 和 stop 记录。

它不是运行时评分器。代码明确把三阶段的完整交付记作日志，最终再统一评分。

但阶段请求仍然使用 `ScenarioRuntime` 的用户事件管理，且后续场景事件依赖仍可能通过参考事件图释放。因此这里存在两层控制：

```text
ScenarioStages：什么时候把下一段用户话发出来
ScenarioRuntime：参考事件和环境事件什么时候完成、释放
```

后续需要确认这两层是否都必要，以及哪些阶段事件应该由真实运行事实推动，哪些只是评分参考。

### 3.3 Gaia2 InteractionVariant：modify / cancel / addtask

交互变体是独立于普通三阶段的本地机制，数据契约是 `gaia2-interaction-variant-v1`。

它可以包含：

- `modify`：根据状态让用户提出修改请求；
- `cancel`：先产生临时请求，再产生取消或变更请求；
- `addtask`：保留原任务后，增加额外任务和参考事件。

变体保留源任务哈希，并在运行时构造一个任务视图。它不是把源任务永久改写，也不是普通参考事件的另一个名称。

当前 `ActiveMetricManager.install()` 会先检查 `variant_for(task)`：如果任务是变体，就安装 `InteractionVariantRuntime`。`run_simulation()` 也会在发现变体时自动准备 active metrics 配置。

这意味着交互变体会主动改变用户请求和后台请求流程。它应被视为一种测试场景机制，不能与“后台任务完成指标”混为一类。

关键入口：

- `src/tau2/domains/gaia2/interaction_variants.py`
- `src/tau2/metrics/active/persistent_task/variant.py`
- `src/tau2/metrics/active/manager.py`
- `src/tau2/runner/simulation.py`

### 3.4 后台动态指标与旧 persistent_task 机制

你提到的“根据当前执行状态追加查询、修改、取消请求”确实存在，而且它与 Gaia2 参考答案触发机制不同。

#### 新 active persistent-task 机制

它的流程是：

```text
观察真实后台任务事件
        ↓
选择一个状态与操作组合
        ↓
等待状态稳定、停留时间和对话边界
        ↓
生成或读取一条动态用户请求
        ↓
通过普通用户交互路径发送
        ↓
观察 Agent 的后台操作和回复
        ↓
独立计算 completion_score 和明细
```

支持的操作类型是：`query`、`result`、`modify`、`cancel`。它根据真实后台任务状态选择请求，并使用明确的证据源记录后台事件。

这条机制**不是参考答案触发器**：

- 它不靠 Gaia2 `scenario.events` 中的参考 Agent 回复来决定是否注入请求；
- 它观察 Provider 提供的后台任务事件；
- 它使用自己的状态策略、请求生成和交付窗口；
- 它的结果独立记录，不默认乘入普通 Gaia2 结果。

交互变体已通过独立的 `ScenarioMechanismManager` 安装，不属于普通 active 指标。

#### 旧 persistent_task 机制（已退役）

旧 `persistent_task_config` 配置入口、integration/coordinator 调度、固定 sidecar、
回放和重新评分链路已移除。运行时不再使用旧机制生成请求、阻塞阶段或组合主任务奖励。

当前后台交互使用 active persistent-task 或独立交互变体场景机制。公共后台事件模型、
Provider 适配器和分数读取函数继续保留；历史结果只读取已有轨迹、摘要和保存分数，
不自动恢复旧运行或重新评分。

## 4. “参考事件触发”与“动态追加请求”的边界

之前的审查把两者放在同一个“参考答案影响运行”的问题里，范围过宽，需要修正：

| 机制 | 主要来源 | 是否有意改变评测流程 | 主要用途 |
|---|---|---:|---|
| Gaia2 参考事件依赖 | 题目 `scenario.events` | 是，可能释放环境事件和脚本请求 | 原始场景因果与环境模拟 |
| ScenarioStages | `scenario.stages`、STOP 和已交付状态 | 是 | 连续多阶段用户请求 |
| InteractionVariant | 变体数据契约 | 是 | 修改、取消、添加任务的测试场景 |
| Active persistent task | 实时后台观察和状态策略 | 是，且这是设计目标 | 动态查询、结果、修改、取消请求 |
| 旧 persistent task（已退役） | 历史结果 | 否 | 读取已保存轨迹和分数 |

因此，后台动态请求不能简单归类为“参考答案污染”。它本来就是你设计的测试流程。但它仍需要和 Gaia2 参考事件触发分开记录，避免最后无法判断某条用户请求究竟来自哪种机制。

当前脚本及追加请求使用以下来源值：

```text
source = scenario | scenario_stage | interaction_variant | active_persistent_task
```

当前 `environment_trace` 中的用户交付记录包含 `source` 和 `purpose`。
每阶段的首条主请求（包括初始请求及中断后的重复交付）归为
`scenario_stage/stage_request`；阶段内其他脚本请求归为
`scenario/scripted_request`。交互变体追加请求使用 `interaction_variant`，
用途为 `temporary` 或 `followup`；active 动态请求使用
`active_persistent_task/followup`。

Stage 来源在 Runtime 初始化时按阶段主请求 ID 登记，保留原有直接交付路径和时机，
不会为了记录来源额外入队。旧轨迹中的来源值保留原样，本次来源命名调整不改变评分规则。

## 5. 当前最影响评测的链路问题

### 5.1 参考回复匹配仍可能控制环境事件

这是真正需要重点讨论的地方，不应和动态后台请求混为一谈。

当前某些环境／后续请求的释放依赖参考事件完成，而参考 Agent 回复完成可能依赖实际 Agent 文本匹配。这样会出现：

```text
Agent 说法合理但与参考文本不同
        ↓
参考回复未绑定
        ↓
依赖事件不释放
        ↓
Agent 没有看到后续本应出现的环境信息
```

这会改变测试条件。后续需要逐类区分：

- 必须由真实业务操作结果触发的环境事件；
- 必须由用户或第三方行为触发的环境事件；
- 原参考 Agent 回复对应的脚本事件；
- 只用于离线评分的参考回复。

不能通过删除所有参考事件来解决，因为环境事件和目标状态仍需要来源。需要把运行时因果和评分参考拆开。

### 5.2 请求来源与诊断读取（已修复）

用户交付轨迹和诊断 `UserInput` 均保留 `source/purpose`。诊断按实际交付的
事件 ID 传递来源，不合并中断或重试记录；历史缺失来源保留空值。

变体摘要从 `scenario_mechanisms.mechanisms.interaction_variant` 读取，普通
active 摘要从 `active_metrics.metrics.persistent_task` 读取。三个管理操作、
请求关系和反馈窗口读取函数共用入口；历史变体旧位置只在新位置缺失时回退。

原始诊断包只保存运行事实，不依赖已有评分；本次不调整各来源进入指标的规则。

### 5.3 诊断采集与实时执行仍有耦合

`EvidenceRecorder` 会在工具调用前后采集应用状态。状态快照和事件记录需要锁；部分 JSON 复制、文件状态读取和哈希过程在工具调用附近执行。

这可能改变工具结果返回和场景时间。当前没有直接证据证明影响已达到某个具体数量，因此先把它列为结构风险：后续应测量一次普通工具调用在开启／关闭诊断时的时间差，再决定是否拆分临界区。

### 5.4 公共媒体事实与评分结果（已修复）

`diagnostics/media.py` 提供 `read_media_activity()`，当前证据直接读取已保存的
语音活动区间，历史音频复用原有检测和媒体映射。语音指标与精简性音频统计均读取
公共事实；精简性不再调用 `evaluate_voice()` 或读取其 `waveform_evidence`。

语音区间与播放时间统一为媒体相对秒。缺失证据和可靠的零语音分开保存；
缺少用户事件分类不会使可用的 Agent 时长统计失效。

### 5.5 ENV、execution 和诊断评分读取不同事实

当前有三种重要事实来源：

- 在线环境累计状态和 `environment_trace`；
- 诊断采集的前后快照及操作证据；
- 离线重放后得到的预测环境状态。

ENV 主要通过重放和参考状态比较，execution 主要通过诊断调用和前后帧，其他指标还读取对话和媒体证据。

这不一定需要立刻改成单一评分器，但需要明确每一项评价的是：

- 实际在线状态；
- 记录的操作事实；
- 重放得到的状态；
- 交付给用户的内容。

否则同一个 Agent 行为可能在不同指标中使用不同版本的“实际结果”。

### 5.6 保存证据与独立评分（已修复）

`run_simulation()` 先保存含 active／变体运行摘要的原始轨迹，再落盘诊断与媒体证据，
最后执行主任务、active、变体及诊断评分。原始轨迹不被最终结果覆盖。

后台与变体评分函数读取可序列化摘要，不再依赖 Controller 或读取新 Provider 事件。
离线诊断调用相同函数；同一次运行的自动诊断复用已计算结果，避免重复裁判请求。

各项评分分别记录失败，不抹去已保存对话，也不阻断其他独立评分。没有保存回调的
低层调用仅保证内存事实先于评分，不声称已经持久化。运行异常沿用现有处理。

## 6. 哪些东西暂时不建议动

- Gaia2 的 ARE 应用实现仍是实际工具行为来源，不能因为它来自旧项目就直接删除。
- 参考执行用于生成目标状态和参考事件，不能当作第二次 Agent 运行删除。
- 三阶段控制、交互变体和后台动态指标各有明确测试目的，不能简单合并成一个“follow-up”开关。
- 旧 persistent task 只保留历史结果读取，运行和重新评分入口已退役。
- 幻觉重试当前对 Qwen Agent 被配置为 0；是否作为框架通用机制保留，属于其他问题。

## 7. 后续逐项讨论顺序

建议接下来按以下顺序处理，每次只解决一类链路问题：

1. **参考事件是否应该继续参与环境事件释放。**先列出必须保留的环境触发和可以改为真实事实触发的事件。
2. **统一动态请求来源。**为三阶段、交互变体、新旧后台机制统一记录来源和用途。
3. **明确各类请求进入哪些指标。**尤其是正式用户请求、动态后台请求、环境脚本消息和内部控制消息。
4. **统一执行事实。**比较在线状态、诊断快照和重放状态，确定各评分的权威输入。
5. **拆开诊断采集与工具临界区。**只在测量确认有影响后做必要修改。
6. **收拢旧入口。**新运行使用确定的主路径，旧路径只承担历史读取和兼容。

本报告没有加入大规模验收计划。后续每个问题都应优先通过数据来源、事件归属和单一事实入口解决；只有机制改动完成后，用少量针对性样例确认行为即可。
